## ADR-001: Magazyn wersjonowany IMGW

**Data:** 2026-10-17  
**Status:** Przyjęta  
**Spec:** `docs/superpowers/specs/2026-10-17-versioned-store-design.md`  
**Plan:** `docs/superpowers/plans/2026-10-17-versioned-store.md`  
**Źródło kontraktu:** `Archiwista/docs/SPEC.md` 4.8, 12.7–12.9; `Archiwista/docs/wymagania-imgwtools.md` IMGW-1..14 i R1..12. Współpraca nie oznacza zależności pakietowej od Archiwisty ani Kartografa.

### Kontekst i warianty

Wydanie 2.1.1 pobiera archiwa do płaskich plików bez wersji, trwałych nagłówków HTTP i pochodzenia; przerwany zapis może zostać uznany za pełny, a różne ścieżki serwera o tej samej nazwie pliku mogą się zderzyć. Opcjonalny cache SQLite obejmuje tylko hydro i nie zachowuje źródłowych bajtów. Konsumenci potrzebują niezmiennych wejść i gotowych szeregów stacji, możliwych do czytania offline i z udziału sieciowego. Rozważono rozwój cache SQLite, współdzielenie formatu/implementacji Kartografa oraz osobny magazyn IMGW. Wybrano osobny magazyn: format stacji i szeregów jest inny niż geodanych, a SQLite/WAL ani mutowalne dowiązania nie mogą być źródłem prawdy na udziale SMB.

### Polityka wersji (IMGW-13) i konsekwencje

Obok pięciu schematów D1 rozszerzenie komórkowe `imgw-pmaxtp/1` stosuje te same reguły `/N`, ale nie jest wymagane przez Archiwistę.

`imgw-project/1` jest edytowalną instrukcją: odrzuca obce klucze strukturalne (IMGW-14), a przyszłe opcjonalne dodatki wolno umieszczać tylko w przewidzianej mapie `extensions` z ignorowaniem nieznanych wpisów. Nowy klucz na najwyższym poziomie wymaga `/2`; ta zasada godzi ścisłą walidację projektu z dodatkami w `/1`.

Pięć identyfikatorów schematów (wraz z `imgw-plan/1`) ma własny licznik `/N`, niezależny od wersji pakietu. W ramach `/1` dodajemy tylko pola opcjonalne, nie zmieniamy znaczenia/typów istniejących; czytniki tolerują dodatkowe pola w plikach magazynu i wynikach, ale manifest projektu jako edytowalna instrukcja jest celowo walidowany ściśle. Zmiana niezgodna wymaga `/2`, jawnego odczytu `/1` i `/2` w okresie przejścia, osobnych przykładów i testów kontraktu; zapis starym kodem do nieznanego znacznika jest zabroniony. `store_info` zgłasza nieobsługiwaną wersję, skan raportuje problem i nie parsuje plików nieznanego schematu; API odczytu w 3.x nie usuwa podpisanych publicznych funkcji ani nie zmienia semantyki `/1` bez nowego major. Każda zmiana schematu i publicznego API trafia do CHANGELOG.

Konsekwencje: archiwa źródłowe zachowują bajty i pochodzenie; stacje bez położenia oraz serie z lukami pozostają widoczne; udział SMB nie wymaga bazy, lecz powielone bajty przy relabelingu i koszt budowania Parquet są świadomym kompromisem. Stary magazyn SQLite nie jest migrowany automatycznie; jego lokalne pliki nie są kasowane przez instalację, a dane pobiera się ponownie do nowego magazynu. Niespójny lub nieznany format zatrzymuje zapis bez cichej konwersji. PMAXTP jest rozszerzeniem IMGWTools ponad zakres Archiwisty v1.0, nie zmienia jego kontraktów stacji/szeregów.

### Erraty

**2026-10-18 — relacja do `docs/OBSERWATOR_SPEC.md`.** Decyzją właściciela z 2026-10-17 magazyn według ADR-001 wchodzi teraz, w wydaniu 3.0.0. Szkic Obserwatora (2026-08-11) zakładał w §7 cache SQLite „schemat v2” i numer 3.0.0 dla rebrandingu; oba założenia są nieaktualne: cache SQLite v2 zastępuje magazyn wersjonowany (D1–D5), a Obserwator pozostaje wyłącznie przyszłą zmianą nazwy i rozszerzeniem o providery w kolejnym wydaniu major. Treść decyzji D1–D11 bez zmian; zmiany wydania opisuje `docs/CHANGELOG.md`.

**2026-10-18 — ADR-002.** Spójność interfejsów rozstrzyga ADR-002 (spec §13). Zastąpione punkty tego wpisu: Q1 — `get_dataset` przyjmuje także slug i alias legacy, a sloty używają pełnego klucza (slug zostaje wyłącznie w nazwach katalogów magazynu); Q6 — CSV użytkownika ma kolumny `station_code,latitude,longitude,source`; D7 — w `fetch_pmaxtp` argument `method` jest wyłącznie nazwany (wywołanie Hydrografu `fetch_pmaxtp(latitude, longitude, method=...)` bez zmian), reszta D7 obowiązuje; D9 („CLI = API”) realizuje generowanie CLI i REST z katalogu komend; spec §12 — `IMGWPlanStaleError` usunięty. Treść D1–D11 bez zmian.

**2026-10-18 — klucze zbiorów (IMGW-20).** Uzupełnienie D4: klucz zbioru ma postać `<kraj>.<przedrostek>.<zbiór>[_<wariant>]` (`DATASET_KEY_PATTERN`, `^[a-z]{2}\.[a-z][a-z0-9]*\.[a-z][a-z0-9_]*$`; test obejmuje cały rejestr i klucz katalogu `pl.imgw.stations`). Klucz opublikowany w wydaniu z magazynem się nie zmienia, a sidecary zachowują surowy `dataset` na zawsze (D1). Zmiana nazwy zbioru jest możliwa wyłącznie przez wpis stary → bieżący klucz w tabeli `DATASET_KEY_ALIASES` (`imgwtools.datasets`; pusta w 3.0.0), odnotowany w `docs/CHANGELOG.md`; tabela jest odrębna od wejściowych `legacy_alias` sprzed 3.0. `read_meta` podaje obok surowego `dataset` znormalizowany `Meta.dataset_key` (`resolve_dataset_key`): bieżący klucz dla klucza aktualnego lub z tabeli, `None` dla klucza poprawnego, lecz nieznanego IMGWTools — bez wyjątku i bez problemu `invalid_meta` w skanie (zgodność wprzód, IMGW-13); klucz niezgodny ze wzorem pozostaje `invalid_meta`. `get_dataset` i odczyty magazynu przyjmują klucze z tabeli. Tożsamość dostawcy wynika z pól `provider` i `country`, nie z części klucza. Treść D1–D11 bez zmian.

**2026-10-19 — ADR-003 (dostawca ČHMÚ).** Według sekcji „Wpływ” ADR-003 (zatwierdzonej 2026-10-18; kod dostawcy wchodzi do wydania 3.0.0 według erraty ADR-003 D16): D4 — klucz zbioru ma postać `<kraj>.<dostawca>.<slug>` (`pl.imgw.*` dla IMGW-PIB, `cz.chmi.*` dla ČHMÚ), a rejestr liczy 17 deskryptorów: 13 IMGW-PIB i 4 ČHMÚ (`cz.chmi.hydro_daily`, `cz.chmi.meteo_daily`, `cz.chmi.hydro_stations`, `cz.chmi.meteo_stations`), z dostawcą opisanym przez `ProviderDescriptor` (ADR-003 D1); katalog stacji ČHMÚ ma własny katalog slotu `stations/versions/chmi_stations/<label>_<sha8>/` (ADR-003 D5). D1 i Q14 — tożsamością wersji pozostaje SHA-256 bajtów, a te same bajty pod nowym sygnałem nadal dają `relabeled` z kopią; dla zbiorów z formą kanoniczną (`content_form` `chmi-json/1`: archiwa hydro ČHMÚ i listy stacji ČHMÚ) inne bajty o tym samym `content_sha256` co bieżąca wersja dają jednak `unchanged` bez nowej wersji, z komunikatem `content_unchanged` (ADR-003 D6, D17), a nowy sygnał źródła trafia do rejestru obserwacji slotu `observations/` (ADR-003 D18). Zbiory bez formy (wszystkie IMGW-PIB i CSV meteo ČHMÚ) zachowują regułę D1 bez zmian. „Polityka wersji (IMGW-13)” — dochodzi kontrakt magazynu `imgw-observation/1` (`observations/<YYYY-MM-DD>_<sha8>.json` w slocie archiwum, `store_info().contracts["observation"]`) z własnym licznikiem `/N`. Treść D1–D11 i odpowiedzi Q1–Q15 bez zmian; szczegóły: spec 2026-10-18 §2, §3, §3.1–§3.2.

**2026-10-19 — publikacja wersji według modelu Kartografa (wszystkie systemy).** Wydanie 3.0.0 publikowało katalog wersji pojedynczym `renameat2(RENAME_NOREPLACE)`, dostępnym wyłącznie na Linuksie; na macOS i Windows każdy zapis do magazynu kończył się `IMGWStoreConflictError`, a na Windows także `fsync` katalogu (`os.open` katalogu) zgłaszał błąd. Decyzją właściciela IMGWTools przyjmuje model publikacji Kartografa (ADR-036 D18, D21, D22 Kartografa), żeby oba magazyny działały tak samo: pliki wersji trafiają z `.incoming/` do katalogu `<label>_<sha8>` dowiązaniami twardymi `os.link` (nigdy nie zastępują celu), sidecar pliku głównego jest dowiązywany ostatni i zatwierdza wersję; katalog bez sidecara jest przerwaną publikacją (pomijaną przy wyborze wersji, zgłaszaną przez skan jako `missing_sidecar`, uzupełnianą przez następny zapis tej samej treści); brak dowiązań twardych → `IMGWStoreConflictError` (`not_atomic`); `fsync` katalogu pomijany na Windows i na systemach plików bez tej operacji. Odrzucone: osobna operacja przemianowania bez zastąpienia dla każdego systemu (`renameatx_np(RENAME_EXCL)` na macOS, `MoveFileExW` na Windows) — zachowuje atomowość całego katalogu, ale utrzymuje trzy ścieżki kodu i rozjeżdża się z Kartografem. Układ magazynu, schematy `/1` i tożsamość wersji (SHA-256) bez zmian; spec 2026-10-17 §3 i spec 2026-10-18 §3.2 mają erraty.

**2026-10-19 — publikacja wersji: wycofanie, wymóg systemu plików i przerwana publikacja.** Uzupełnienie erraty powyżej, przed tagiem 3.0.0 (decyzja właściciela). (1) Wycofanie po błędzie albo Ctrl+C w trakcie publikacji nie usuwa dowiązanych już plików danych: równoległy zapis tych samych bajtów mógł je przejąć (plik o tej samej nazwie i tym samym SHA-256 zostaje) i zatwierdzić swoim sidecarem, więc ich usunięcie zostawiało zatwierdzoną wersję bez pliku głównego (`missing_file`, `IMGWDataError` dla całego slotu). Zostaje przerwana publikacja, a znikają wyłącznie puste katalogi utworzone przez ten zapis; dowiązany sidecar nie jest nigdy usuwany. Wersję nadal zatwierdza wyłącznie sidecar pliku głównego, a zatwierdzona wersja zawsze ma swoje pliki danych. (2) Wymóg systemu plików jest ten sam co w magazynie Kartografa (jego ADR-036 D22) i obejmuje także znacznik `imgw-store.json`, publikowany jak dotąd `os.link`: FAT, exFAT, część NAS i FUSE oraz klient SMB macOS dają w `init_store` i w każdym zapisie `IMGWStoreConflictError` (`not_atomic`); odczyt dowiązań nie wymaga. Odrzucone: wyłączne `open(..., "xb")` dla znacznika — usuwa wymóg tylko dla znacznika, a zapis wersji i tak potrzebuje dowiązań. (3) Przerwanej publikacji nie dokończy zapis pod inną etykietą (katalog stacji — data budowy, PMAXTP i archiwum bez `Last-Modified` — data pobrania, UTC) ani zapis innej treści; magazyn nie sprząta wersji automatycznie, więc taki katalog `<label>_<sha8>/` bez sidecara usuwa się ręcznie, gdy nie trwa żaden zapis (w trakcie zapisu równoległy pisarz mógłby właśnie przejmować jego pliki).

**2026-10-19 — `meteo_kind` w katalogu IMGW-PIB.** Spec §8 wymienia `meteo_kind` (`climate|precipitation|null`), a rozstrzygnięcie T11 ustaliło zawsze `null` („żadne źródło katalogu nie rozróżnia stacji klimatycznych i opadowych”). Rozróżniają je jednak indeksy bieżących szeregów, które już są źródłem katalogu — pomiarem, nie zgadywaniem z kodu. Reguła (poprawka B audytu zgodności z Archiwistą): stacja meteorologiczna z bieżącej wersji szeregu `pl.imgw.meteo_climate_daily` ma `climate`, w przeciwnym razie stacja z bieżącego szeregu `pl.imgw.meteo_precip_daily` — `precipitation`, bez takiego szeregu `null`. Stacja z obu szeregów jest klimatologiczna, bo program stacji klimatologicznej obejmuje opad. Katalog ČHMÚ ma zawsze `null` (ČHMÚ nie publikuje klasy stacji). `check_catalog` zgłasza akcję indeksów szeregów jako `newer` także przy różnicy `meteo_kind`. Pole i schemat bez zmian (wartości już dozwolone w `/1`).

**2026-10-24 — D3, Q3 (superseded by ADR-007).** The marker `imgw-store.json` gains `tool`, `producer_version` and an always present `created_at` (`created_by` stays); the first write into an empty or new root creates it, and a root with the layout and no marker is `store_unavailable` until `imgw store init` verifies it (ADR-007 D6). Q3's probe of Kartograf by `kartograf-project.json` and `kartograf-meta/1` sidecars is replaced by the marker file names `kartograf-store.json` and `imgw-store.json` in ancestors, at the root and in descendants. The layout of D3 is unchanged.

## ADR-002: Jeden katalog komend i spójne interfejsy

**Data:** 2026-10-18  
**Status:** Przyjęta  
**Spec:** `docs/superpowers/specs/2026-10-17-versioned-store-design.md` §13 — normatywny dla Pythona, CLI, REST i web; w razie sprzeczności ma pierwszeństwo przed §1–§12  
**Plan:** `docs/superpowers/plans/2026-10-17-versioned-store.md`, sekcja „ADR-002” (U01–U16, fale 10–17)  
**Źródło:** audyt spójności interfejsów z 2026-10-18 (ustalenia z dowodami `plik:linia`, sprawdzone offline na gałęzi `feature/versioned-store`). Właściciel zatwierdził pełną unifikację w 3.0.0 ze zmianami niezgodnymi; jedyne wywołanie Hydrografu, `fetch_pmaxtp(latitude, longitude, method=...)`, działa bez zmian.

### Kontekst i warianty

Po wdrożeniu ADR-001 ta sama operacja ma kilka postaci zależnie od interfejsu:

- **Zasięg.** Katalog komend obejmuje magazyn, projekt i `fetch hydro|meteo`. Dane bieżące, ostrzeżenia, PMAXTP live oraz listy stacji i zbiorów obsługują ręczne komendy CLI i trasy REST z własnym `httpx`, a web — własne parsowanie CSV i budowanie URL-i. `GET /api/v1/hydro|meteo/stations` zwraca dwie zaszyte stacje-przykłady, a `imgw list stations` wymaga pandas i pliku z osobnego skryptu. Część operacji istnieje w jednym interfejsie: rekordy szeregu tylko w REST, `series select` tylko w CLI i Pythonie, `read_catalog`/`read_station_list` tylko w Pythonie, `pmaxtp check|read` bez REST, ostrzeżenia bez REST.
- **Nazwy.** `lat`/`lon` w katalogu, a `latitude`/`longitude` w funkcjach i REST; `dataset` (lista) obok `datasets`; `no_series` obok `series`; pięć kodowań lat (`year` z zakresem, `years`, `start_year`/`end_year`, `years: list[int]`, `start`/`end`); kod stacji jako `station_code`, `station_id`, `station` i `id`; rodzina jako `kind`, `--type`, `data_type` i `warning_type`; `--output` raz plikiem, raz katalogiem; `version` liczona względem root, CWD albo tylko `series/versions/`; `-m` raz `--method`, raz `--month`; `method` raz domyślne, raz wymagane.
- **Identyfikatory.** Pełne klucze, slugi, polskie słowa interwałów i enumy współistnieją z dwiema prywatnymi tabelami konwersji; REST przyjmuje `data_type=hydro`, a zwraca `dane_hydrologiczne`; trzy gramatyki slotów sprawiają, że slot z raportu synchronizacji nie działa w `current_version`; dwa układy CSV współrzędnych (`id,X,Y` i `station_code,lon,lat,source`).
- **Błędy i wyniki.** `IMGWError` nie ma kodu maszynowego. Te same złe współrzędne dają 422 z angielską listą pydantic, 400 `{code, detail}`, kod 1 z tekstem na stdout albo kod 1 z `Błąd: …` na stderr. CLI kończy kodem 1 każdy błąd i każdy częściowy wynik, REST zwraca 409 z raportem tylko dla `stale_plan`, a `IMGWPlanStaleError` nie jest nigdzie zgłaszany. REST gubi komunikaty `on_notice`, w tym warunki licencji IMGW-PIB.
- **Braki.** Stronicowanie istnieje tylko w zaślepkach; pokrycia szeregu nie odczyta się z CLI; katalog nie ma postaci JSON Schema poza Pythonem, a modele REST są ręcznymi kopiami katalogu, które już się rozjechały (`datasets`/`dataset`, `series`/`no_series`, brak zakresów lat).

Warianty: (a) udokumentować różnice i zostawić interfejsy; (b) dodać warstwy tłumaczące stare nazwy obok nowych (aliasy, shimy); (c) uczynić katalog komend jedynym źródłem operacji, generować z niego CLI i REST, a web oprzeć wyłącznie na funkcjach publicznych. Wybrano (c) w całości w 3.0.0: (a) utrwala błędy potwierdzone w audycie, (b) podwaja powierzchnię testów i przeczy czystemu przejściu z ADR-001, a wydanie 3.0.0 i tak zawiera zmiany niezgodne.

### Konsekwencje

Jedna implementacja walidacji, nazw, błędów, statusu i stronicowania obsługuje cztery interfejsy, a test parytetu — ta sama komenda w Pythonie, CLI i REST daje tę samą kopertę — staje się możliwy dla każdej komendy. Skrypt lub agent poznaje całą powierzchnię z `imgw commands schema` albo `GET /api/v1/commands/schema` i odróżnia błąd wejścia, brak obiektu, konflikt, awarię źródła i wynik częściowy po kodzie, bez parsowania tekstu. Koszt: przepisanie adapterów CLI, REST i web oraz ich testów (U01–U16), większy rejestr zbiorów (13 deskryptorów), zmiany niezgodne wobec 2.1.1 i wobec niewydanego stanu deweloperskiego 3.0.0. REST odpowiada 200 również dla koperty `partial`/`failed`, więc klient musi czytać pole `status`. Python zachowuje wygodę: funkcje zwracają pełne wyniki, a koperta dotyczy `run_command`/`check_command`.

### Zmiany niezgodne

Pełna tabela stare → nowe: spec §13.11. Wobec 2.1.1:

- **Python:** `fetch_hydro_current` i `fetch_synop` — `station_id` → nazwany `station`, pola `station_id` → `station_code`; `fetch_warnings(warning_type)` → `fetch_warnings(*, kind=None)`, pole `warning_type` → `kind`; `fetch_pmaxtp` — `method` wyłącznie nazwany; `list_hydro_stations`, `list_meteo_stations`, `get_hydro_stations_with_coords` (z wariantami `_async`), `HydroStation`, `MeteoStation` → `find_stations`, `fetch_hydro_states`, `StationListEntry`, `HydroState`; `build_hydro_url`, `build_meteo_url`, `get_available_years`, `DownloadURL` i enumy `DataType`, `HydroInterval`, `HydroParam`, `MeteoInterval`, `MeteoSubtype`, `PMaXTPMethod` → rejestr (`archive_files`, `get_dataset`); `build_pmaxtp_url(method, latitude, longitude)` → `build_pmaxtp_url(latitude, longitude, *, method)`; `build_api_url(..., station_id=)` → `station=`.
- **CLI:** grupy `imgw fetch` i `imgw list` usunięte (zastępują je `datasets download|list`, `current …`, `pmaxtp fetch`, `stations find`); wynik to koperta JSON; błąd to JSON na stderr i kod z rejestru zamiast 1; opcja `-o PLIK` komend live usunięta (przekierowanie stdout); `fetch hydro|meteo` nie mają domyślnego interwału.
- **REST:** trasy `/api/v1/hydro/*`, `/api/v1/meteo/*`, `/api/v1/download/*` i `/api/v1/pmaxtp/{methods,url,data}` zastąpione trasami katalogu; błędy w `application/problem+json`; walidacja 400 zamiast 422; pola modeli REST = pola modeli biblioteki.
- **Pliki:** `python -m imgwtools.reference_data` zapisuje `hydro_stations_locations.csv` z nagłówkiem `station_code,latitude,longitude` i nie zapisuje już `hydro_stations_names.csv`/`meteo_stations_names.csv` (czytała je tylko usunięta `imgw list stations`).

Wobec niewydanego stanu 3.0.0 sprzed tego ADR: `run_command`/`check_command` zwracają `CommandResult`; `IMGWPlanStaleError` usunięty; `store read` → `store export`; opcje `lat`/`lon`, `dataset` (lista) i `no_series` → `latitude`/`longitude`, `datasets`, `series`; `method` domyślnie `POT`; sloty według nowej gramatyki; `StationCoverage.station` i `ProjectFile.station` (`imgw-project.json`) → `station_code`; CSV użytkownika `station_code,latitude,longitude,source`; trasy REST magazynu według §13.3 (`/store/entries` → `/store/scan`, `/series/{station}` → `/series/read`, `/series/index` → `/series/summary`, `/pmaxtp/store/sync` → `/pmaxtp/sync`, `POST /series/export` i `POST /store/check` → `GET`); kody REST `store_not_configured|store_root_invalid|user_locations_invalid` → `store_unavailable`, `writes_disabled|write_token_missing|invalid_api_key` → `forbidden`, a 409 `stale_plan` → koperta `partial`.

## ADR-003: Dostawca ČHMÚ w magazynie IMGW

**Data:** 2026-10-18  
**Status:** Przyjęta (2026-10-18, zatwierdzenie właściciela) — D2 i D17: poszerzenie kontraktów `/1` w C01 przed tagiem v3.0.0; D18 rozstrzyga pytanie otwarte o sygnał po `unchanged` przy innych bajtach  
**Spec:** `docs/superpowers/specs/2026-10-18-chmi-provider-design.md` (plan C01–C10 w §16)  
**Źródło kontraktu:** `Archiwista/docs/wymagania-imgwtools.md` IMGW-15..19 (sekcje 4.15–4.19, priorytet P3, Archiwista v0.6 „PL + CZ”), stan z commita Archiwisty `4435cf7` (IMGW-15 i IMGW-16 po uwagach IMGWTools; wcześniej `a59c6bc`); w granicach ADR-001 i ADR-002.  
**Źródło faktów:** rozpoznanie opendata.chmi.cz na żywo 2026-10-18 (hydrologia, klimatologia, licencja i nagłówki HTTP); w spec każdy fakt źródła ma oznaczenie [V] (zweryfikowane), [I] (wniosek) albo [U] (otwarte).

### Kontekst i warianty

Archiwista v0.6 pokazuje stacje ČHMÚ w tych samych widokach co stacje IMGW i czyta je tym samym adapterem, więc ČHMÚ musi być dostawcą w kontraktach ADR-001 i w katalogu komend ADR-002, a nie osobnym produktem. Szkic `docs/OBSERWATOR_SPEC.md` (2026-08-11) planował dla ČHMÚ warstwę providerów z własnymi modelami, wyjątkami i REST `/api/v2` w wydaniu 4.0.0; ADR-001 i ADR-002 ustaliły od tego czasu magazyn, rejestr, sloty, kody błędów i kopertę, a rozpoznanie z 2026-10-18 obaliło część założeń szkicu (strefa czasu, układ plików, inwentarz przez sondowanie 404).

Fakty przesądzające projekt [V 2026-10-18]:

- Archiwa są per stacja. Hydro: plik JSON na stację i rok kalendarzowy (`hydrology/historical/data/daily/H_<WIGOS>_DQ_<rok>.json`; 39 291 plików, 803 stacje, lata 1887–2025, 605 MB). Meteo: plik JSON na stację za całą historię (z kopertą; łącznie 25,4 GB, największy 149 MB) albo plik CSV na stację i element bez koperty (`historical_csv`). Brak paczek „cały kraj”; zbiór stacja × rok ma dziury (102 stacje z brakującymi latami, brak pliku = 404).
- `ETag` to nginx `"<hex mtime>-<hex size>"`, nie suma treści. Serwer masowo publikuje ponownie: 38 733 pliki hydro dobowe mają mtime 2025-07-01, a wszystkie 1 537 plików meteo dobowych — 2026-09-04; czy bajty się przy tym zmieniają, nie wiadomo [U].
- JSON meteo i wszystkie pliki metadanych mają kopertę `zaznamID`/`datumVytvoreni`, zmienianą przy każdej generacji: te same dane, inna suma SHA-256. Pliki `historical` hydro i CSV meteo koperty nie mają.
- Listing katalogu (nginx autoindex) podaje nazwę, mtime (UTC, z dokładnością do minuty) i rozmiar każdego pliku: jedno GET listingu (5,3 MB) zastępuje 39 291 żądań HEAD.
- Hydro nie ma flag ani kodów braku (brak = brak wiersza); meteo ma `FLAG` i `QUALITY` 0–5, a brak to pusty `VALUE` z `QUALITY 4`.
- Serwer przechowuje wyłącznie najnowszą wersję pliku. Licencja to CC BY 4.0 bez narzuconej formuły atrybucji. Nie ma odpowiednika PMAXTP.

Warianty: (a) osobna warstwa providerów według szkicu Obserwatora; (b) ČHMÚ jako kolejne deskryptory rejestru w kontraktach 3.x, po otwarciu dziedzin wartości `/1` przed wydaniem 3.0.0; (c) jak (b), ale z `/2` kontraktów po wydaniu 3.0.0. Wybrano (b), z (c) jako jawnym wariantem awaryjnym: (a) dubluje rejestr, błędy i interfejsy ujednolicone w ADR-002 i wymaga drugiego adaptera Archiwisty; (c) zmusza IMGWTools i Archiwistę do czytników `/1` i `/2`, choć 3.0.0 nie ma jeszcze tagu, a kontrakty `/1` nie zostały wydane (ADR-002 D14).

### Wpływ na ADR-001 i ADR-002

Po zatwierdzeniu (2026-10-18) do wpisów ADR-001 i ADR-002 dopisuje się datowane erraty, bez przepisywania treści: ADR-001 D4 i ADR-002 D4 — klucze `<kraj>.<dostawca>.<slug>` zamiast wyłącznie `pl.imgw.*` i rejestr 17 deskryptorów; ADR-001 D1 i Q14 — dla zbiorów z formą kanoniczną inne bajty o tej samej treści dają `unchanged` bez wersji (D6, D17), a nowy sygnał trafia do rejestru obserwacji (D18); ADR-001 „Polityka wersji (IMGW-13)” — nowy kontrakt magazynu `imgw-observation/1` (D18); spec 2026-10-17 §2 — kod stacji według gramatyki dostawcy zamiast „dokładnie 9 cyfr”; §3 — wiersz `content_unchanged` w regule `write_archive` i katalog `observations/` slotu archiwum; §4 — pola `content_sha256` i `content_form` sidecara; §9 — `StoreEntry.kind="observation"` i `contracts["observation"]`; §10.1 i §11.6 — opcjonalne `content_sha256` i `content_form` pinu, status `restored_by_content` i stan `content_match`; §11 — dziedziny z D2; §13.2–§13.4 — opcje `provider` i `stations`, komenda `datasets providers`, deskryptory ČHMÚ; §13.5 — tytuł `source_unavailable`; §13.7 — sloty ČHMÚ.

### Konsekwencje

Archiwista czyta ČHMÚ tym samym adapterem i kontraktami, a zachowanie IMGW się nie zmienia; obu dostawców obejmuje jedna reguła wersji, rozszerzona o treść kanoniczną wyłącznie dla zbiorów z formą (D17). Koszty: listing hydro dobowych (5,3 MB bez kompresji) przy każdym sprawdzeniu; masowa ponowna publikacja z tymi samymi bajtami daje `relabeled` z kopią wszystkich plików wybranych stacji (np. 30 stacji × 60 lat × ok. 15 KB ≈ 27 MB i 1 800 par HEAD+GET); pełne lustro kraju oznacza 39 291 katalogów slotów w jednym katalogu (celem jest wybór stacji, nie lustro); dane bieżącego roku pojawiają się dopiero po publikacji `historical` (D4). Koszty D17 i D18: ponowna publikacja z innymi bajtami o tej samej treści kosztuje jedno HEAD+GET na plik (2–33 KB na plik hydro) i jedną obserwację (ok. 0,6 KB) na nowy sygnał, po czym `check_store` pokazuje plik jako `current` aż do następnej zmiany sygnału; rejestr obserwacji to nowy element układu slotu i nowy kontrakt magazynu (`imgw-observation/1`), który muszą znać czytniki 3.0.0 (C01); treść niezgodna z formą blokuje zapis wersji (odstępstwo od zapisu archiwów bez parsowania, tylko dla zbiorów z formą); piny ČHMÚ mają dwa dodatkowe pola, a Archiwista musi obsłużyć `restored_by_content`, `content_match` i wpisy `observation`. Ryzyka: `historical_csv` nie jest zbiorem o wysokiej wartości, więc ciągłość publikacji nie ma gwarancji prawnej; nie wiadomo, czy regeneracja zachowuje bajty (jeśli nie: JSON z formą daje `unchanged` z obserwacją, a CSV meteo — nową wersję przy każdej regeneracji); listing nie wykryje przepisania pliku w tej samej minucie z tym samym rozmiarem; czytnik 3.0.0 pokaże wpisy ČHMÚ jako problemy `unknown_entry`; przypięcia ČHMÚ są odtwarzalne ze źródła tylko do następnej zmiany treści (D14).

## ADR-004: Wsparcie agentów AI w wydaniu 3.0.0

**Data:** 2026-10-19  
**Status:** Przyjęta (2026-10-19; zakres i wydanie 3.0.0 przesądził właściciel, decyzje D1–D12 przyjął koordynator wdrożenia w ramach udzielonej mu odpowiedzialności za architekturę)

**Źródło:** ADR-002 D14 (poza zakresem 3.0.0 zostały: AGENTS.md/llms.txt, opisy angielskie, serwer MCP, porządkowanie komunikatów legacy); decyzja właściciela przekazana 2026-10-19 (te cztery pozycje oraz kod dostawcy ČHMÚ, C02–C10, wchodzą do 3.0.0); specyfikacja MCP 2026-07-28 (*Tools*), SDK `mcp` 2.3.0 (PyPI, 2026-10-02), llms.txt v2 (llmstxt.org), agents.md; potrzeby Retmana (`Retman/docs/ARCHITECTURE.md` 3.2–4.3, 8.1) i Archiwisty (`Archiwista/docs/SPEC.md` 5.2, 7, 12.7). Fakty o kodzie z commita `d8cb11c` (2026-10-19), pomiary z tego dnia.

### Kontekst i warianty

ADR-002 dał maszynowy interfejs: jeden katalog komend z `command_schema()`, kopertę `imgw-result/1`, zamknięty rejestr kodów błędów i kody wyjścia. Agentom AI brakowało jednak: (1) zwięzłego przewodnika (kiedy sprawdzać, jak czytać kopertę, jakie klucze zbiorów, czego nie robić), zgodnego z kodem; (2) tekstów innych niż polskie — dla agentów i narzędzi anglojęzycznych (manifest Retmana ma opisy po angielsku); (3) wejścia MCP, przez które klienci (asystenci w edytorach, aplikacje czatu) wołają narzędzia bez CLI; (4) spójności tekstów — w kodzie zostały komunikaty bez polskich znaków i po angielsku. Katalog nie mówił też, które komendy zapisują pliki albo łączą się ze źródłem, więc żaden adapter nie mógł bezpiecznie ograniczyć agenta do odczytu.

Warianty: (a) dokumentacja pisana ręcznie i zewnętrzny serwer MCP (osobny pakiet albo projekt społeczności); (b) wszystko w pakiecie i z katalogu: przewodnik jako plik pochodny, metadane skutków i opisy angielskie w katalogu, serwer MCP jako czwarty adapter obok CLI, REST i web; (c) jak (b), ale w 3.1.0. Wybrano (b) w 3.0.0 (wydanie przesądził właściciel): (a) powtarza błąd sprzed ADR-002 — ręczne kopie katalogu, które się rozjeżdżały — i drugą implementację wywołań; (c) wydałoby `imgw-commands/1` bez metadanych skutków, które potem musiałyby dojść jako zmiana kontraktu.

Po zatwierdzeniu (A06) dopisuje się datowane erraty, bez przepisywania treści: ADR-002 D1 — katalog 37 komend (`datasets providers` z ADR-003, `commands guide` z ADR-004), poza katalogiem także `imgw mcp`, `GET /llms.txt` i punkt `/mcp`; D2 — tekst dla człowieka po polsku domyślnie, wariant angielski tekstów katalogu i rejestrów według D3; D14 — pozycje „poza zakresem” realizuje ADR-004 w 3.0.0; spec 2026-10-17 §13.1 p. 5 (język), §13.2 (opcja `lang`, wartości `format` `agents|llms`), §13.3 (`commands guide`, `lang` w `commands schema`, 37 komend), §13.5 (`title_en`; `forbidden` także w MCP), §13.9 (pola typów z D2–D3), §13.10 (CLI `IMGW_LANG`, REST `Accept-Language`, adapter MCP); ADR-003 D13 — „razem 36 komend” → 37; spec 2026-10-18 §9.3 — liczba komend.

### Konsekwencje

Agent poznaje IMGWTools z jednego źródła zgodnego z kodem (`AGENTS.md`, `llms.txt`, `imgw commands guide`), a każdy klient MCP dostaje te same komendy, walidację, kopertę i kody co CLI i REST, domyślnie bez możliwości zapisu. Katalog po raz pierwszy deklaruje skutki komend, z czego korzystają MCP, przewodnik i Retman. Koszty: zależności dodatku `mcp` (m.in. `httpx2`, `pyjwt[crypto]`, `opentelemetry-api`, `pydantic>=2.12`); ok. 26 KB schematów narzędzi w kontekście modelu (35 komend, pomiar 2026-10-19); ok. 160 tekstów angielskich utrzymywanych razem z polskimi (2026-10-19: 35 opisów komend, 60 różnych pomocy opcji, 14 reguł, 8 grup, 12 tytułów błędów, 13 tytułów zbiorów; ČHMÚ i `commands guide` dokładają kilkanaście); regeneracja plików pochodnych przy każdej zmianie katalogu; ustawienia `IMGW_LANG`, `IMGW_MCP_ALLOW_WRITES`, `IMGW_MCP_ENABLED`, `IMGW_MCP_ALLOWED_HOSTS`; 37. komenda. Ryzyka: zmiany API SDK w 2.x (przypięcie `<3`, testy w pamięci), polski `detail` dla agentów anglojęzycznych, obciążenie źródeł przez pętle agentów (przewodnik, adnotacje, limit `nginx`).

### Pytania otwarte

- **Do właściciela:** (1) zatwierdzenie D1–D12 — rozstrzygnięte 2026-10-19 (status „Przyjęta”); (2) czy publiczny serwer ma włączyć `/mcp` (`IMGW_MCP_ENABLED`).
- **Po 3.0.0:** (3) tłumaczenie treści wykonania (`detail`, `Notice.text`); (4) filtr narzędzi MCP według grup albo dostawcy (`data_commands(provider=…)`, ADR-003 D13); (5) limit wywołań sieciowych serwera stdio; (6) zapis przez MCP po HTTP z autoryzacją.

Zadanie ścieżki zapisu zmienia `IMGW_STORE_ROOT` na `IMGW_ROOT`, ustawia domyślny korzeń `<data_dir>/imgw` (i raportuje go w `config show`) oraz musi uznawać `api_keys.json` w tym katalogu za plik spoza układu magazynu.

### Pytania otwarte

- Czy stan serwera (klucze API) ma mieć własny katalog zamiast `<data_dir>/imgw` (egzekwowanie kluczy jest w backlogu, `docs/PROGRESS.md`).

## ADR-006: Message catalog and English machine output

**Date:** 2026-10-24  
**Status:** Accepted  
**Standard:** Nogat 2.1, AGI-9.1, AGI-9.2, AGI-6.4, DEV-2.1, DEV-2.3, ECO-042; ADR-004 D2–D3 (the limits it recorded)  

### Context and options

AGI-9.2 makes every machine output English (`--json`, the error line of the CLI, MCP results,
REST without `Accept-Language`, OpenAPI, `AGENTS.md`, `llms.txt`) and leaves Polish to the
human-readable output on request; DEV-2.3 keeps user-facing text in translation resources, not
inline. ADR-004 translated only the catalog texts (`help_en`, `description_en`, `title_en`) and
left the `detail` of every error, the text of every notice and the progress lines Polish, so an
agent got Polish by default. Options: (a) gettext with `.po` files; (b) `locales/pl.toml` keyed by
the English sentence; (c) Python catalogs keyed by English IDs with both texts side by side; (d)
English literals at the raise sites and a Polish dictionary keyed by the sentence.

### Decisions D1–D7

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Catalog.** The package `imgwtools.messages`; one module per area (`messages/<area>.py`) with `MESSAGES: dict[str, Text]`; `Text(en, pl)` (English first); the key is `<area>.<name>` in snake_case; placeholders are `str.format` fields with plain names (a brace in the text is `{{`). A text and its translation are edited together. | (a) a compile step, no static check of keys, plural forms the texts do not need; (b), (d) the key changes with every edit of the English sentence. |
| D2 | **`Message`.** `message(key, lang="en", **values)` renders an entry as a `Message`: a `str` that remembers its key, values and language. `Message.localized(lang)` renders it again (a `Message` among the values too), `localize(text, lang)` gives a plain `str` (a final text), `IMGWError.localized(lang)` does it for a `detail`. An f-string, `+` or `join` of a message is plain text: composition happens inside a template and a message is passed as a value. | A parser of the text; a language argument threaded through every function. |
| D3 | **Where a text is rendered.** The raise site and the notice give English (a `Message`). REST (`problem_response`), MCP (`_error`) and the web GUI render it for their caller; `CommandResult.to_json(lang=)` and `jsonable(lang=)` render the texts of a result and of its notices (English by default); the last stderr line of the CLI is always English; the progress and notice lines of the CLI follow `IMGW_LANG`. | A Polish `detail` with an English title (ADR-004 D3). |
| D4 | **Defaults (AGI-9.2).** English: `--json`, the CLI error line, MCP (`imgw mcp --lang`, `create_server`, `http_app`), REST without `Accept-Language`, OpenAPI, `command_schema`, `list_commands`, `agent_guide` and the committed `AGENTS.md`/`llms.txt`. Polish on request or by setting: the CLI help and human lines (`IMGW_LANG`, default `pl`, DEV-18.1), the web GUI (its templates are Polish, DEV-15.2), `Accept-Language: pl`, `imgw mcp --lang pl`, `--lang pl` of the description commands. | |
| D5 | **Registry.** `ErrorSpec.title` is a `Message`; `title_en` is removed without an alias. `Lang` and `LANGS` (`("en", "pl")`) live in `imgwtools.messages`. | |
| D6 | **Guards.** `tests/unit/test_messages.py`: both languages of an entry are not empty and have the same placeholders, every `message("<literal>")` call names an entry and gives exactly its placeholders, no entry is unused, and no Polish literal is left outside the catalog (the two Polish keys of the IMGW-PIB JSON are the only allowance). During the migration the files that still held Polish were a `_PENDING` set grouped by area; it is empty and gone. | |
| D7 | **Catalog texts.** English is authoritative for the texts of the command catalog and the registries (AGI-9.1): `help`, `description`, `rules`, the group titles, the dataset titles and the notes of the ČHMÚ variables are catalog messages (`messages/commands.py`, `messages/datasets.py`); `CommandOption.help`, `DataCommand.description` and `DataCommand.rules` hold the English `Message`, `help_en`, `description_en`, `rules_en` and `DatasetDescriptor.title_en` are removed without an alias, and `command_schema(lang=)` renders the language asked for with `localize`. | |

### Consequences

An agent reads the same English text whatever the user's setting, and a Polish user keeps Polish human output. Each area moves in its own commit (exceptions, notices, CLI, REST, MCP, guide), so the defaults of an interface flip together with the texts it shows. A new text costs two strings in a catalog and one `message("<key>", name=value)` call; the guard test fails on a missing translation, a wrong placeholder, an unused entry and a stray Polish literal. A text assembled by an f-string at a call site is not translatable and is a defect.

### Open questions

- Whether the reasons of the internal validators (a `ValueError` whose text another message embeds) need a Polish variant: they are catalog messages where a person reads them and plain English where only a developer does.

### Errata

The texts the guide composes itself (column titles, effect classes, flow titles and notes, the rules shared with the MCP instructions, flag syntax lines) are the catalog area `agent_guide`; the Markdown templates in `_data/agents/` stay one file per format and language.

**2026-10-24 — D3, D4 (REST).** `accept_language` falls back to English (it was Polish), so a REST answer without a usable `Accept-Language` is English. **2026-10-24 — D1, D3 (areas, rendering).** Two catalog areas hold wordings that persisted files or other tools read: `legal` (attribution formulas and the IMGW-PIB name, one wording in both languages) and the reason of a failed HTTP request, which the `_http_error` helper classifies by its prefix, not by a Polish text. A list that a message embeds is joined with `"; "`. The two texts of a plan item (`not published`, `cancelled`) are English, and Retman and Archiwista compare them literally (PROGRESS, Next 2).

## ADR-007: Data output: plain mode, the store and the default root

**Date:** 2026-10-24  
**Status:** Accepted (the author approved the Nogat convention on 2026-10-24; this ADR applies it to IMGWTools)  
**Standard:** Nogat 2.1, DEV-19.1 to DEV-19.20, DEV-18.2, AGI-3.4, AGI-5.8, ERR-1, ECO-051; changes D3 and Q3 of ADR-001  

### Context and options

IMGWTools wrote data in three unrelated ways: the versioned store with a required `--root` (and `IMGW_STORE_ROOT` for the CLI), a plain archive download to `--output` (default `./data/downloaded`, `.part` files, no check of existing files) and exports to `--path`. A nested store was recognised by Kartograf's sidecars, not by a marker, and the store statuses said `created` where Kartograf says `new`. ECO-051 and DEV §19 give every tool with a store the same two modes. Options: (a) keep the three paths and add aliases; (b) one convention for every writing command, as DEV §19 says (chosen); (c) a shared store library (rejected in the Nogat plan: a dependency between projects). IMGWTools 3.0.0 is untagged, so the breaking changes land before its first release without migration.

### Decisions D1–D9

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Names (DEV-19.1).** `output_dir` (`-o`, `--output-dir`, `path_role` output) writes plain files, `root` (`--root`, `-r`, `path_role` root) writes the store, `output` (`--output`, no short form, `path_role` output) writes exactly one file (`store export`, `series export`, `commands guide`; it replaces `path`, and `force` replaces an existing file). `output_dir` and `root` are one exclusion group: giving both is `validation_error` (`details.reason="exclusive_options"`, `details.option` the second of the two given, `details.options` the group `["output_dir", "root"]`). `output` of an export and the `root` that names the store it reads do not exclude each other; an export has no store mode, so its `output_in_store` hint asks for a file outside every store and does not name `--root`. `force` without `output` is `validation_error` (`details.option="output"`). The previous `output` (a directory), `path` and `-p` are removed without an alias. | An alias of `--path`; `-o` as a store root. |
| D2 | **Default root (DEV-19.2, DEV-18.2).** Neither `output_dir` nor `root`: the store at the first of `--root`, `IMGW_ROOT`, `[imgw] root` of `nogat.toml` and `<data_dir>/imgw`. `IMGW_STORE_ROOT` is renamed `IMGW_ROOT` without an alias; the setting is `Settings.root`. `root` is optional in every store command; `validate_command` fills it in (Python, CLI, MCP stdio), and `imgw config show --json` reports the root, its source, whether it exists and its size. A project task has no `root` (the project store). `stations find` takes the default only with `source=store`. The state file `api_keys.json` of the server lives in the default root and is not store content. | A required root; a default in the working directory. |
| D3 | **Plain mode (DEV-19.4 to DEV-19.9).** `datasets download`, `store sync` and `pmaxtp sync` write plain files with `output_dir`. The name of a file is its name in the store; because names of one request can collide, the relative sub-path is the server path (`<dir>/<server_path>`; PMAXTP: `<METHOD>/<indX>_<indY>/cell.json` and `response.json`). The selection is the one of the store; IMGWTools declares no selection rule of its own, so `skipped_incomplete` is not used. No sidecar, no hard link, no `versions/`, so it works on FAT, exFAT and SMB. Two limits of "the names are known before the transfer": the PMAXTP cell is named by the indices of the answer, so only a call that gives `ind_x` and `ind_y` is refused before the request, any other after the one small answer and before the first file is written (a deviation of DEV-19.5 and DEV-19.6, listed in `CLAUDE.md`); the ČHMÚ station files are found by the store on a server listing that a plain write does not use, so plain `store sync` needs `years` for them (`validation_error`, `details.reason="years_required_in_plain_mode"`). In plain mode `PlanAction` has the optional fields `action` (`write`, `replace`, `conflict`), `path` and `reason`; a plan that lists conflicts has status `ok` and exit 0, and only the real run fails with `conflict`. `check_command` returns the same plan as `--check`. | A failing plan. |
| D5 | **Output in a store (DEV-19.11).** An `output_dir` or `output` that is, lies inside or would enter a directory that holds `kartograf-store.json` or `imgw-store.json` is `conflict` with `details.reason="output_in_store"`; the hint of `output_dir` says to use `--root`, the hint of an export's `output` to choose a file outside every store. The check looks at the marker file names only; nothing is imported from Kartograf. | D6 | **Store marker (DEV-19.12 to DEV-19.14).** `imgw-store.json` (`imgw-store/1`) always has `schema`, `tool` (`imgw`), `created_at` and `producer_version` and keeps `created_by`. The first write into an empty or new root creates it, as `init_store` does; a root that has `archives/`, `series/`, `stations/` or `pmaxtp/` and no marker is `store_unavailable` with the hint `imgw store init --root <path>`, and `store init` verifies the layout (every sidecar is `imgw-meta/1`, no Kartograf layout) before it writes the marker. The server state `api_keys.json` is the only file an empty root may hold. A store never nests: before a write the command looks for `kartograf-store.json` and `imgw-store.json` in the ancestors of the root, at the root (the other tool's marker) and in its descendants, and a nested store is `conflict` with `details.reason="nested_store"`. The detection of Kartograf by `kartograf-project.json` and `kartograf-meta/1` sidecars (ADR-001 Q3) is removed. | A required `store init`; probing foreign sidecars. |
| D7 | **Statuses and results (DEV-19.19).** `created` is `new` in `VersionResult`, `OperationResult`, `SeriesReport`, `CatalogReport` and `PMaXTPStoreResult`; a reused series version is `unchanged`; plain files are `written` or `replaced`. | D8 | **Command classes (DEV-19.17, DEV-19.18).** Store-only: `store init`, `store catalog`, `series build` and `project *` (their input or result is the store), and the options `plan` and `series` of `store sync`: with `output_dir` they are `validation_error` (`details.reason="store_only_option"`, hint `--root`). | D9 | **Servers and sidecars (DEV-19.3, DEV-19.16).** REST writes only to `IMGW_ROOT`, only with writes enabled and the token, never to the default root, and accepts no `root`, `output_dir` or `output` (nor `force` or a plan file) in a request: they are server or local options and a request that carries one is `validation_error`. `imgw mcp` writes only inside its `--allow-dir` directories and only with `--allow-writes`: every path option and the default root must lie inside one, otherwise `forbidden` (`details.reason="outside_allowed_dirs"`); without `--allow-dir` a writing tool, and any call that names a place to write (`output`, `output_dir`, the `plan` file), is `forbidden` (`no_allowed_dir`) and only a plan is possible. ### Consequences

An agent or a script writes without a flag (the default store), writes plain files with `-o`, and gets the same names, errors, plan and `files[]` as in Kartograf. A call that wrote to `./data/downloaded` now fails with a hint or writes to the store. The default root `<data_dir>/imgw` also holds the API keys of the server, which is why the marker, not emptiness, decides what a root is. The plain engine (`imgwtools.output`) is written once and shared by the three commands and the exports. Consumers that read `status == "created"`, `DownloadReport.output` or the exports' `path` (Retman, Archiwista, Hydrolog) change with the pin (PROGRESS).

### Open questions

- Whether `store sync` in plain mode should offer a freshness check against the server (HEAD) before it replaces a file; it replaces on `--force` only, as DEV-19.9 says.
- Whether `series build` of a plain-mode tree should exist (DEV-19.18 makes derived data from stored versions store-only).

### Errata

**2026-10-25 — D6 (what a reader needs of the marker).** D6 says the marker "keeps `created_by`"; it is a field the writer writes, not one a reader needs. DEV-19.12 asks of a marker at least `schema`, `tool`, `created_at` and `producer_version`, and `open_store` has always taken any marker whose `schema` is `imgw-store/1`, while `store_info`, `iter_store` and every reader behind `current_version` refused a marker without a `created_by` text (`invalid_marker`). A root the writer had opened and completed (`prepare_store` adds `tool`, `created_at` and `producer_version`, never `created_by`) therefore could not be read, which Archiwista found. The reader now needs only `schema`, as `open_store` does (one rule on both sides, held by a test over the markers each side takes or refuses); `created_by` stays in the marker `init_store` writes, the packaged `imgw-store/1` schema lists it as an optional field instead of a required one, and the marker never gains it afterwards. The message `reader.marker_has_no_valid_created` is removed. This only widens what a reader accepts, so the contract stays `imgw-store/1`.

**2026-10-25 — D9 (the typed sidecar).** D9 says the sidecar already has the DEV-19.16 core; the typed `Meta` that `read_meta`, `iter_store` and `current_version` return now exposes the two fields of it that the reader validated and dropped, `producer` and `producer_version` (a consumer that cannot read them states the package itself and loses the version of an older write). They are the sidecar's own values: a version written by an earlier release keeps its older number and the version of the reading package never stands in, and since `imgw-meta/1` requires both, a sidecar without one stays `invalid_meta` and is refused, not filled in. The contract test of the sidecar core compares them with the file for every kind of version of both providers. Both fields are optional in the dataclass (defaults `"imgwtools"` and `None`), so `imgw-meta/1` and the constructors of `Meta` are unchanged.

**2026-10-25 — Consequences (the requests of Archiwista, the incremental scan).** Archiwista asked for four additions to the read API, all inside `/1` (AGI-4.1) and none a change of the files: the marker that a reader needs only `schema` of (D6, above), a code beside each text of `StoreInfo.problems` (`problem_codes`; the vocabulary `missing_store`, `missing_marker`, `invalid_marker`, `unsupported_store` is the one `iter_store` already used and is not renamed), `Meta.producer` and `Meta.producer_version` (D9, above) and an `iter_store` that takes the versions a consumer already knows. The last is `iter_store(skip_versions=…)`, a mapping of the version directory (relative to the root, with `/`) to the names of its data files: the shape of `ScanScope.known_versions` of Archiwista and of `skip_versions` of Kartograf (AGI-1.2). Such a version comes back with `skipped=True` and no `meta`, without its directory being listed, its sidecar read or its file measured; a version never changes, which is why the caller can vouch for it. The scan still lists the slots, so a new version, a problem and a version that is gone show as in a full scan, and an observation is still checked against the content fields of the version it names (that sidecar is read on demand). Rejected: a "since" time, which says nothing of a removed, replaced or broken version; a plain collection of directories, which would list each of them to find the main file of an archive; an option of `store scan`, because a list of known versions does not belong in a query string or a command line, so the parameter exists in Python only.
