## ADR-001: Versioned IMGW store

**Date:** 2026-10-17  
**Status:** Accepted; the project parts (D1, Q1, Q2, version policy) superseded by ADR-008 (2026-10-31)  
**Spec:** `docs/superpowers/specs/2026-10-17-versioned-store-design.md`  
**Plan:** `docs/superpowers/plans/2026-10-17-versioned-store.md`  
**Contract source:** `Archiwista/docs/SPEC.md` 4.8, 12.7–12.9; `Archiwista/docs/wymagania-imgwtools.md` IMGW-1..14 and R1..12. Cooperation does not mean a package dependency on Archiwista or Kartograf.

### Context and options

Release 2.1.1 downloads archives into flat files without versions, persistent HTTP headers or provenance; an interrupted write can be taken as complete, and different server paths with the same file name can collide. The optional SQLite cache covers only hydro and does not keep the source bytes. Consumers need immutable inputs and ready station series, readable offline and from a network share. The options considered were extending the SQLite cache, sharing Kartograf's format/implementation, and a separate IMGW store. A separate store was chosen: the format of stations and series differs from that of geodata, and neither SQLite/WAL nor mutable links can be the source of truth on an SMB share.

### Version policy (IMGW-13) and consequences

Besides the five schemas of D1, the cell extension `imgw-pmaxtp/1` applies the same `/N` rules, but it is not required by Archiwista.

> **Superseded by ADR-008** (2026-10-31) where it speaks of the project manifest: `imgw-project/1` is removed and projects moved to Archiwista; the policy holds for the other contracts.

`imgw-project/1` is an editable instruction: it rejects foreign structural keys (IMGW-14), and future optional additions may be placed only in the designated `extensions` map, with unknown entries ignored. A new top-level key requires `/2`; this rule reconciles strict project validation with additions in `/1`.

The five schema identifiers (together with `imgw-plan/1`) have their own `/N` counter, independent of the package version. Within `/1` we add only optional fields and do not change the meaning/types of existing ones; readers tolerate extra fields in store files and results, but the project manifest, as an editable instruction, is deliberately validated strictly. A breaking change requires `/2`, explicit reading of `/1` and `/2` during the transition period, separate examples and contract tests; writing to an unknown marker with old code is forbidden. `store_info` reports an unsupported version, the scan reports a problem and does not parse files of an unknown schema; the read API in 3.x does not remove signed public functions or change the semantics of `/1` without a new major. Every change of a schema and of the public API goes into the CHANGELOG.

Consequences: source archives keep their bytes and provenance; stations without a location and series with gaps stay visible; an SMB share needs no database, but duplicated bytes on relabeling and the cost of building Parquet are a deliberate trade-off. The old SQLite store is not migrated automatically; its local files are not deleted by the installation, and the data is downloaded again into the new store. An inconsistent or unknown format stops the write without a silent conversion. PMAXTP is an IMGWTools extension beyond the scope of Archiwista v1.0; it does not change Archiwista's station/series contracts.

**2026-10-18 — dataset keys (IMGW-20).** Addition to D4: a dataset key has the form `<country>.<prefix>.<dataset>[_<variant>]` (`DATASET_KEY_PATTERN`, `^[a-z]{2}\.[a-z][a-z0-9]*\.[a-z][a-z0-9_]*$`; the test covers the whole registry and the catalog key `pl.imgw.stations`). Next to the raw `dataset`, `read_meta` gives the normalized `Meta.dataset_key` (`resolve_dataset_key`): the current key for a current key or one from the table, `None` for a key that is valid but unknown to IMGWTools — without an exception and without an `invalid_meta` problem in the scan (forward compatibility, IMGW-13); a key that does not match the pattern remains `invalid_meta`. `get_dataset` and the store reads accept keys from the table. The provider identity follows from the fields `provider` and `country`, not from a part of the key. The text of D1–D11 is unchanged.

**2026-10-19 — ADR-003 (ČHMÚ provider).** According to the "Impact" section of ADR-003 (approved 2026-10-18; the provider code enters release 3.0.0 under the ADR-003 D16 erratum): D4 — a dataset key has the form `<country>.<provider>.<slug>` (`pl.imgw.*` for IMGW-PIB, `cz.chmi.*` for ČHMÚ), and the registry counts 17 descriptors: 13 IMGW-PIB and 4 ČHMÚ (`cz.chmi.hydro_daily`, `cz.chmi.meteo_daily`, `cz.chmi.hydro_stations`, `cz.chmi.meteo_stations`), with the provider described by `ProviderDescriptor` (ADR-003 D1); the ČHMÚ station catalog has its own slot directory `stations/versions/chmi_stations/<label>_<sha8>/` (ADR-003 D5). D1 and Q14 — the version identity remains the SHA-256 of the bytes, and the same bytes under a new signal still give `relabeled` with a copy; for datasets with a canonical form (`content_form` `chmi-json/1`: ČHMÚ hydro archives and ČHMÚ station lists), however, different bytes with the same `content_sha256` as the current version give `unchanged` without a new version, with the notice `content_unchanged` (ADR-003 D6, D17), and the new source signal goes into the slot's observation register `observations/` (ADR-003 D18). Datasets without a form (all IMGW-PIB ones and the ČHMÚ meteo CSV) keep the D1 rule unchanged. "Version policy (IMGW-13)" — the store contract `imgw-observation/1` is added (`observations/<YYYY-MM-DD>_<sha8>.json` in the archive slot, `store_info().contracts["observation"]`) with its own `/N` counter. The text of D1–D11 and of answers Q1–Q15 is unchanged; details: spec 2026-10-18 §2, §3, §3.1–§3.2.

**2026-10-19 — version publication following Kartograf's model (all systems).** Release 3.0.0 published a version directory with a single `renameat2(RENAME_NOREPLACE)`, available only on Linux; on macOS and Windows every write to the store ended with `IMGWStoreConflictError`, and on Windows the directory `fsync` (`os.open` of a directory) also raised an error. By the owner's decision IMGWTools adopts Kartograf's publication model (Kartograf's ADR-036 D18, D21, D22), so that both stores behave the same: version files go from `.incoming/` into the `<label>_<sha8>` directory as `os.link` hard links (they never replace the target), the sidecar of the main file is linked last and commits the version; a directory without a sidecar is an interrupted publication (skipped when choosing a version, reported by the scan as `missing_sidecar`, completed by the next write of the same content); no hard links → `IMGWStoreConflictError` (`not_atomic`); the directory `fsync` is skipped on Windows and on file systems without this operation. Rejected: a separate no-replace rename operation for each system (`renameatx_np(RENAME_EXCL)` on macOS, `MoveFileExW` on Windows) — it keeps the atomicity of the whole directory, but maintains three code paths and diverges from Kartograf. The store layout, the `/1` schemas and the version identity (SHA-256) are unchanged; spec 2026-10-17 §3 and spec 2026-10-18 §3.2 have errata.

**2026-10-19 — version publication: rollback, file system requirement and interrupted publication.** Addition to the erratum above, before the 3.0.0 tag (owner's decision). (1) A rollback after an error or Ctrl+C during publication does not remove data files already linked: a parallel write of the same bytes could have taken them over (a file with the same name and the same SHA-256 stays) and committed them with its sidecar, so removing them left a committed version without its main file (`missing_file`, `IMGWDataError` for the whole slot). An interrupted publication remains, and only empty directories created by this write disappear; a linked sidecar is never removed. A version is still committed only by the sidecar of the main file, and a committed version always has its data files. (2) The file system requirement is the same as in Kartograf's store (its ADR-036 D22) and also covers the marker `imgw-store.json`, published with `os.link` as before: FAT, exFAT, some NAS and FUSE systems and the macOS SMB client give `IMGWStoreConflictError` (`not_atomic`) in `init_store` and in every write; reading does not require links. Rejected: an exclusive `open(..., "xb")` for the marker — it removes the requirement only for the marker, and writing a version needs links anyway. (3) An interrupted publication is not completed by a write under another label (station catalog — build date, PMAXTP and an archive without `Last-Modified` — download date, UTC) or by a write of other content; the store does not clean up versions automatically, so such a `<label>_<sha8>/` directory without a sidecar is removed manually when no write is running (during a write a parallel writer could be taking over its files at that moment).

**2026-10-19 — `meteo_kind` in the IMGW-PIB catalog.** Spec §8 lists `meteo_kind` (`climate|precipitation|null`), and the T11 resolution set it always to `null` ("no catalog source distinguishes climate and precipitation stations"). They are, however, distinguished by the indexes of the current series, which are already a catalog source — by measurement, not by guessing from the code. Rule (fix B of the Archiwista compliance audit): a meteorological station from the current version of the `pl.imgw.meteo_climate_daily` series has `climate`, otherwise a station from the current `pl.imgw.meteo_precip_daily` series has `precipitation`, and without such a series `null`. A station in both series is climatological, because the programme of a climate station includes precipitation. The ČHMÚ catalog always has `null` (ČHMÚ does not publish a station class). `check_catalog` reports the series index action as `newer` also on a difference in `meteo_kind`. The field and the schema are unchanged (the values are already allowed in `/1`).

**2026-10-24 — D3, Q3 (superseded by ADR-007).** The marker `imgw-store.json` gains `tool`, `producer_version` and an always present `created_at` (`created_by` stays); the first write into an empty or new root creates it, and a root with the layout and no marker is `store_unavailable` until `imgw store init` verifies it (ADR-007 D6). Q3's probe of Kartograf by `kartograf-project.json` and `kartograf-meta/1` sidecars is replaced by the marker file names `kartograf-store.json` and `imgw-store.json` in ancestors, at the root and in descendants. ## ADR-002: One command catalog and consistent interfaces

**Date:** 2026-10-18  
**Status:** Accepted; the parts on projects (D1, D4, D9, D10, D11, D14, breaking changes) superseded by ADR-008 (2026-10-31)  
**Spec:** `docs/superpowers/specs/2026-10-17-versioned-store-design.md` §13 — normative for Python, CLI, REST and web; in case of conflict it takes precedence over §1–§12  
**Plan:** `docs/superpowers/plans/2026-10-17-versioned-store.md`, section "ADR-002" (U01–U16, waves 10–17)  
**Source:** interface consistency audit of 2026-10-18 (findings with `file:line` evidence, checked offline on the `feature/versioned-store` branch). The owner approved full unification in 3.0.0 with breaking changes; Hydrograf's only call, `fetch_pmaxtp(latitude, longitude, method=...)`, works unchanged.

### Context and options

After ADR-001 was implemented, the same operation takes several forms depending on the interface:

- **Scope.** The command catalog covers the store, the project and `fetch hydro|meteo`. Current data, warnings, live PMAXTP and the lists of stations and datasets are handled by hand-written CLI commands and REST routes with their own `httpx`, and in the web by its own CSV parsing and URL building. `GET /api/v1/hydro|meteo/stations` returns two hard-coded sample stations, and `imgw list stations` requires pandas and a file produced by a separate script. Some operations exist in only one interface: series records only in REST, `series select` only in the CLI and Python, `read_catalog`/`read_station_list` only in Python, `pmaxtp check|read` without REST, warnings without REST.
- **Names.** `lat`/`lon` in the catalog, but `latitude`/`longitude` in the functions and REST; `dataset` (a list) alongside `datasets`; `no_series` alongside `series`; five encodings of years (`year` with a range, `years`, `start_year`/`end_year`, `years: list[int]`, `start`/`end`); the station code as `station_code`, `station_id`, `station` and `id`; the family as `kind`, `--type`, `data_type` and `warning_type`; `--output` sometimes a file, sometimes a directory; `version` resolved relative to root, the CWD or only `series/versions/`; `-m` sometimes `--method`, sometimes `--month`; `method` sometimes defaulted, sometimes required.
- **Identifiers.** Full keys, slugs, Polish interval words and enums coexist with two private conversion tables; REST accepts `data_type=hydro` but returns `dane_hydrologiczne`; three slot grammars mean that a slot from a sync report does not work in `current_version`; two coordinate CSV layouts (`id,X,Y` and `station_code,lon,lat,source`).
- **Errors and results.** `IMGWError` has no machine-readable code. The same bad coordinates yield 422 with an English pydantic list, 400 `{code, detail}`, code 1 with text on stdout, or code 1 with `Błąd: …` on stderr. The CLI exits with code 1 on every error and every partial result, REST returns 409 with a report only for `stale_plan`, and `IMGWPlanStaleError` is not raised anywhere. REST loses `on_notice` notices, including the IMGW-PIB license terms.
- **Gaps.** Pagination exists only in stubs; series coverage cannot be read from the CLI; the catalog has no JSON Schema form outside Python, and the REST models are hand-written copies of the catalog that have already drifted apart (`datasets`/`dataset`, `series`/`no_series`, missing year ranges).

Options: (a) document the differences and leave the interfaces as they are; (b) add layers translating old names alongside the new ones (aliases, shims); (c) make the command catalog the sole source of operations, generate the CLI and REST from it, and base the web exclusively on public functions. (c) was chosen in full in 3.0.0: (a) perpetuates the errors confirmed in the audit, (b) doubles the test surface and contradicts the clean cutover of ADR-001, and the 3.0.0 release contains breaking changes anyway.

### Decisions D1–D14

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Catalog = every operation.** `data_commands()` describes 35 commands in eight groups — `datasets`, `stations`, `current`, `pmaxtp`, `store`, `series`, `project`, `commands` (list: spec §13.3) — including live reads (`current hydro\|meteo\|synop\|warnings\|hydro-states`, `pmaxtp fetch\|url`), station search (`stations find`) and the dataset registry (`datasets list\|files\|download`). Each command calls exactly one function from `imgwtools.__all__`, and each of its options is a parameter of that function with the same name (the only exception: the envelope options `limit`/`offset`, D9). ### Consequences

One implementation of validation, names, errors, status and pagination serves four interfaces, and a parity test — the same command in Python, CLI and REST yields the same envelope — becomes possible for every command. A script or agent learns the whole surface from `imgw commands schema` or `GET /api/v1/commands/schema` and tells apart an input error, a missing object, a conflict, a source failure and a partial result by code, without parsing text. Cost: rewriting the CLI, REST and web adapters and their tests (U01–U16), a larger dataset registry (13 descriptors), breaking changes relative to 2.1.1 and to the unreleased development state of 3.0.0. REST responds 200 also for a `partial`/`failed` envelope, so the client must read the `status` field. Python keeps its convenience: functions return full results, and the envelope concerns `run_command`/`check_command`.

### Breaking changes

Full old → new table: spec §13.11. Relative to 2.1.1:

- **Python:** `fetch_hydro_current` and `fetch_synop` — `station_id` → keyword `station`, fields `station_id` → `station_code`; `fetch_warnings(warning_type)` → `fetch_warnings(*, kind=None)`, field `warning_type` → `kind`; `fetch_pmaxtp` — `method` keyword-only; `list_hydro_stations`, `list_meteo_stations`, `get_hydro_stations_with_coords` (with their `_async` variants), `HydroStation`, `MeteoStation` → `find_stations`, `fetch_hydro_states`, `StationListEntry`, `HydroState`; `build_hydro_url`, `build_meteo_url`, `get_available_years`, `DownloadURL` and the enums `DataType`, `HydroInterval`, `HydroParam`, `MeteoInterval`, `MeteoSubtype`, `PMaXTPMethod` → the registry (`archive_files`, `get_dataset`); `build_pmaxtp_url(method, latitude, longitude)` → `build_pmaxtp_url(latitude, longitude, *, method)`; `build_api_url(..., station_id=)` → `station=`.

**2026-10-25 — D2, D13 (example calls; AGI-2.2, AGI-2.1).** Every catalog command declares at least one example: a complete `imgw` line and an excerpt of its result, published as `x-imgw.examples` (`[{call, result}]`) of `command_schema` and so of the whole `imgw-commands/1` document. ## ADR-003: ČHMÚ provider in the IMGW store

**Date:** 2026-10-18  
**Status:** Accepted (2026-10-18, owner approval) — D2 and D17: widening of the `/1` contracts in C01 before the v3.0.0 tag; D18 settles the open question about the signal after `unchanged` with different bytes; D14 and the parts of D2, D17, D18 about projects superseded by ADR-008 (2026-10-31)  
**Spec:** `docs/superpowers/specs/2026-10-18-chmi-provider-design.md` (plan C01–C10 in §16)  
**Contract source:** `Archiwista/docs/wymagania-imgwtools.md` IMGW-15..19 (sections 4.15–4.19, priority P3, Archiwista v0.6 "PL + CZ"), as of Archiwista commit `4435cf7` (IMGW-15 and IMGW-16 after IMGWTools' comments; previously `a59c6bc`); within the bounds of ADR-001 and ADR-002.  
**Source of facts:** live survey of opendata.chmi.cz on 2026-10-18 (hydrology, climatology, license and HTTP headers); in the spec every source fact is marked [V] (verified), [I] (inference) or [U] (open).

### Context and options

Archiwista v0.6 shows ČHMÚ stations in the same views as IMGW stations and reads them with the same adapter, so ČHMÚ must be a provider in the contracts of ADR-001 and in the command catalog of ADR-002, not a separate product. The draft `docs/OBSERWATOR_SPEC.md` (2026-08-11) planned for ČHMÚ a provider layer with its own models, exceptions and REST `/api/v2` in release 4.0.0; since then ADR-001 and ADR-002 have settled the store, the registry, slots, error codes and the envelope, and the survey of 2026-10-18 disproved some of the draft's assumptions (time zone, file layout, inventory by probing for 404).

Facts that decide the design [V 2026-10-18]:

- Archives are per station. Hydro: one JSON file per station and calendar year (`hydrology/historical/data/daily/H_<WIGOS>_DQ_<year>.json`; 39,291 files, 803 stations, years 1887–2025, 605 MB). Meteo: one JSON file per station for its whole history (with an envelope; 25.4 GB in total, the largest 149 MB) or one CSV file per station and element without an envelope (`historical_csv`). There are no "whole country" bundles; the station × year set has holes (102 stations with missing years, missing file = 404).
- `ETag` is nginx's `"<hex mtime>-<hex size>"`, not a content checksum. The server republishes in bulk: 38,733 daily hydro files have mtime 2025-07-01, and all 1,537 daily meteo files have 2026-09-04; whether the bytes change in the process is unknown [U].
- Meteo JSON and all metadata files have a `zaznamID`/`datumVytvoreni` envelope that changes with every generation: same data, different SHA-256 checksum. The hydro `historical` files and the meteo CSV files have no envelope.
- The directory listing (nginx autoindex) gives the name, mtime (UTC, to the minute) and size of every file: one GET of the listing (5.3 MB) replaces 39,291 HEAD requests.
- Hydro has no flags or missing-value codes (missing = no row); meteo has `FLAG` and `QUALITY` 0–5, and a missing value is an empty `VALUE` with `QUALITY 4`.
- The server keeps only the latest version of a file. The license is CC BY 4.0 with no imposed attribution wording. There is no PMAXTP equivalent.

Options: (a) a separate provider layer as in the Obserwator draft; (b) ČHMÚ as further registry descriptors in the 3.x contracts, after opening the value domains of `/1` before release 3.0.0; (c) as (b), but with `/2` of the contracts after release 3.0.0. (b) was chosen, with (c) as an explicit fallback option: (a) duplicates the registry, errors and interfaces unified in ADR-002 and requires a second Archiwista adapter; (c) forces IMGWTools and Archiwista to have `/1` and `/2` readers, although 3.0.0 has no tag yet and the `/1` contracts have not been released (ADR-002 D14).

### Impact on ADR-001 and ADR-002

After approval (2026-10-18), dated errata are appended to the ADR-001 and ADR-002 entries without rewriting their text: ADR-001 D4 and ADR-002 D4 — keys `<country>.<provider>.<slug>` instead of only `pl.imgw.*`, and a registry of 17 descriptors; ADR-001 D1 and Q14 — for datasets with a canonical form, different bytes with the same content give `unchanged` without a version (D6, D17), and the new signal goes to the observation register (D18); ADR-001 "Version policy (IMGW-13)" — the new store contract `imgw-observation/1` (D18); spec 2026-10-17 §2 — station code according to the provider's grammar instead of "exactly 9 digits"; §3 — the `content_unchanged` row in the `write_archive` rule and the `observations/` directory of the archive slot; §4 — the sidecar fields `content_sha256` and `content_form`; §9 — `StoreEntry.kind="observation"` and `contracts["observation"]`; §10.1 and §11.6 — the pin's optional `content_sha256` and `content_form`, the status `restored_by_content` and the state `content_match`; §11 — the domains from D2; §13.2–§13.4 — the options `provider` and `stations`, the command `datasets providers`, the ČHMÚ descriptors; §13.5 — the `source_unavailable` title; §13.7 — ČHMÚ slots.

### Consequences

Archiwista reads ČHMÚ with the same adapter and contracts, and IMGW behavior does not change; both providers are covered by one version rule, extended with canonical content only for datasets with a form (D17). Costs: the daily hydro listing (5.3 MB uncompressed) on every check; a bulk republication with the same bytes gives `relabeled` with a copy of all files of the selected stations (e.g. 30 stations × 60 years × approx. 15 KB ≈ 27 MB and 1,800 HEAD+GET pairs); a full mirror of the country means 39,291 slot directories in a single directory (the goal is a selection of stations, not a mirror); current-year data appear only after the `historical` publication (D4). Costs of D17 and D18: a republication with different bytes of the same content costs one HEAD+GET per file (2–33 KB per hydro file) and one observation (approx. 0.6 KB) per new signal, after which `check_store` shows the file as `current` until the next signal change; the observation register is a new element of the slot layout and a new store contract (`imgw-observation/1`) that 3.0.0 readers must know (C01); content that does not conform to the form blocks writing a version (a departure from storing archives without parsing, only for datasets with a form); ČHMÚ pins have two additional fields, and Archiwista must handle `restored_by_content`, `content_match` and `observation` entries. Risks: `historical_csv` is not a high-value dataset, so continuity of publication has no legal guarantee; it is not known whether regeneration preserves the bytes (if not: JSON with a form gives `unchanged` with an observation, and meteo CSV a new version at every regeneration); the listing will not detect a file rewritten within the same minute with the same size; a 3.0.0 reader will show ČHMÚ entries as `unknown_entry` problems; ČHMÚ pins can be restored from the source only until the next content change (D14).

### Open questions

- **For the owner — settled 2026-10-18 by approval of the ADR:** (1) D2 and D17 accepted: widening of the `/1` contracts in C01 before the v3.0.0 tag, the `/2` option as a fallback only; (2) the identifier `CHMI` and the D7 statuses; (3) no `recent` data in the store (D4); (4) persistent recording of the observed signal — the observation register (D18) instead of a persistent `newer`.
- **For ČHMÚ** (chmi@chmi.cz): (5) whether the timestamps in `historical` are in UTC or in fixed SEČ, and how the HD and QD day is defined; (6) the official hydrological year; (7) whether regenerations preserve the file bytes and whether there is a register of corrections (e.g. station `0-203-1-456505`, correction 2026-02-06); (8) continuity and determinism of `historical_csv`; (9) the meaning of `WGS_ELE`, `RICKM`, `HA`, `QA`, `CEVT`, `PRF_ID`, and whether the gauge datum is published; (10) the full `FLAG` dictionary (e.g. `R` for SCE outside `meta3`) and the offset of the precipitation sums of automatic stations (05:40Z).

### Errata

**2026-10-19 — D6, byte comparison (C02).** "Relative to the current version of the slot" in D6 applies only to canonical content. The same bytes are compared, as in ADR-001 (spec 2026-10-17 §3), with every version of the slot with the same SHA-256, including ones older than the current one (the same signal → `unchanged`, a new one → `relabeled`); different bytes with the `content_sha256` of the current version → `unchanged` with an observation of the new signal (D17, D18), and content equal only to an older version → a new version. IMGW behavior unchanged; the text of D6 is unchanged; details: spec 2026-10-18 §3.1 (erratum C02).

**2026-10-19 — D16, release (owner's decision).** The ČHMÚ provider code (C02–C10) goes into release 3.0.0, not 3.1.0. References to "3.1.0" in spec 2026-10-18 and in C10 are to be read as 3.0.0; the CHANGELOG describes ČHMÚ in the 3.0.0 section. The text of D16 is unchanged.

**2026-10-19 — D11, thresholds and the `StationFeature` type (C06).** The `thresholds` property of the ČHMÚ catalog is an object (spec 2026-10-18 §7.3–§7.4), so `StationFeature.properties` has the type `Mapping[str, str | int | float | bool | Mapping[str, object] | None]`: an object value only for `thresholds` of ČHMÚ hydro stations, the other properties are simple as in 3.0.0, and `read_catalog` accepts this object. The only sources of thresholds are `hydrology/now/metadata/meta1.json` and the archive `cz.chmi.hydro_stations` (1 → 3): `meta3.json` gives only the name, river, `HLGP4` and location (§5.3), hence `thresholds.source` ∈ {`chmi_hydro_now`, `chmi_hydro_stations`} (§7.4); "thresholds 1 → 2 → 3" in §7.2 is imprecise. The text of D11 is unchanged; details: spec 2026-10-18 §16 (erratum C06).

## ADR-004: AI agent support in release 3.0.0

**Date:** 2026-10-19  
**Status:** Accepted (2026-10-19; the owner decided the scope and release 3.0.0, the implementation coordinator accepted decisions D1–D12 under the responsibility for the architecture delegated to them)  
**Spec:** `docs/superpowers/specs/2026-10-19-agent-support-design.md` (plan A01–A06 in §11)  
**Source:** ADR-002 D14 (left outside the scope of 3.0.0: AGENTS.md/llms.txt, English descriptions, an MCP server, cleanup of legacy messages); the owner's decision communicated on 2026-10-19 (these four items and the ČHMÚ provider code, C02–C10, go into 3.0.0); MCP specification 2026-07-28 (*Tools*), SDK `mcp` 2.3.0 (PyPI, 2026-10-02), llms.txt v2 (llmstxt.org), agents.md; the needs of Retman (`Retman/docs/ARCHITECTURE.md` 3.2–4.3, 8.1) and Archiwista (`Archiwista/docs/SPEC.md` 5.2, 7, 12.7). Code facts from commit `93a91a3` (2026-10-19), measurements from that day.

### Context and options

ADR-002 provided a machine interface: one command catalog with `command_schema()`, the `imgw-result/1` envelope, a closed registry of error codes, and exit codes. AI agents, however, still lacked: (1) a concise guide (when to check, how to read the envelope, which dataset keys, what not to do), consistent with the code; (2) texts other than Polish — for English-speaking agents and tools (Retman's manifest has English descriptions); (3) an MCP entry point through which clients (assistants in editors, chat applications) call tools without the CLI; (4) consistency of texts — the code still contained messages without Polish diacritics and in English. The catalog also did not say which commands write files or connect to the source, so no adapter could safely restrict an agent to reading.

Options: (a) hand-written documentation and an external MCP server (a separate package or a community project); (b) everything in the package and from the catalog: the guide as a derived file, effect metadata and English descriptions in the catalog, the MCP server as a fourth adapter next to CLI, REST and web; (c) as (b), but in 3.1.0. Option (b) was chosen, in 3.0.0 (the owner decided the release): (a) repeats the mistake from before ADR-002 — hand-made copies of the catalog that drifted apart — and adds a second implementation of calls; (c) would release `imgw-commands/1` without effect metadata, which would later have to be added as a contract change.

### Consequences

An agent learns IMGWTools from a single source consistent with the code (`AGENTS.md`, `llms.txt`, `imgw commands guide`), and every MCP client gets the same commands, validation, envelope and codes as the CLI and REST, with no ability to write by default. For the first time the catalog declares the effects of commands, which MCP, the guide and Retman use. Costs: the dependencies of the `mcp` extra (incl. `httpx2`, `pyjwt[crypto]`, `opentelemetry-api`, `pydantic>=2.12`); approx. 26 KB of tool schemas in the model context (35 commands, measured 2026-10-19); approx. 160 English texts maintained together with the Polish ones (2026-10-19: 35 command descriptions, 60 distinct option help texts, 14 rules, 8 groups, 12 error titles, 13 dataset titles; ČHMÚ and `commands guide` add a dozen or so); regeneration of the derived files on every catalog change; the settings `IMGW_LANG`, `IMGW_MCP_ALLOW_WRITES`, `IMGW_MCP_ENABLED`, `IMGW_MCP_ALLOWED_HOSTS`; a 37th command. Risks: SDK API changes in 2.x (pin `<3`, in-memory tests), Polish `detail` for English-speaking agents, load on the sources from agent loops (guide, annotations, `nginx` limit).

## ADR-005: User environment (DEV-18)

**Date:** 2026-10-24  
**Status:** Accepted  
**Standard:** Nogat 1.0, DEV-18.1–DEV-18.6, ECO-028; the `data-output` convention (Z2)  

### Context and options

Standard 2.1 gives the tools a single user environment: `nogat.toml`, `NOGAT_*` variables, a data directory and a cache directory, no writes in the working directory, credentials only from the environment, and `<tool> config show --json`. IMGWTools used twenty `IMGW_*` variables without a settings file, and `IMGW_DATA_DIR` meant the reference data directory (`hydro_stations_locations.csv`, `desc/`), whereas DEV-18.2 gives `data_dir` the meaning of the parent directory of the stores. Retman exports `IMGW_DATA_DIR` as its `reference_data_dir`. Options: (a) keep `IMGW_DATA_DIR` as the reference directory and deviate from DEV-18.2; (b) give `data_dir` the meaning from the standard and name the reference directory separately; (c) as (b), but with the old name as an alias. Option (b) was chosen (the coordinator's decision, 2026-10-24): before the 3.0.0 tag a breaking change is acceptable (ECO-020), and the alias of (c) would leave two meanings for one variable.

### Decisions D1–D6

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Order of sources (DEV-18.1).** Command-line option, `IMGW_<KEY>`, the same key in `.env`, `NOGAT_<KEY>` (shared keys `data_dir`, `cache_dir`, `lang`), the `[imgw]` section, the `[nogat]` section (shared keys), default value. The `nogat.toml` file is read by `tomllib` (`_environment.py`, without `pydantic-settings` and without the `nogat` package); a missing file is not an error, an unreadable file is a `validation_error` on every `imgw` invocation and at REST server start. Server state (`IMGW_API_KEYS_FILE`) by default in `<data_dir>/imgw/api_keys.json`. A breaking change, no alias. | An alias for the old name; reference data in `data_dir`. |
| D3 | **Credentials (DEV-18.4).** `IMGW_STORE_WRITE_TOKEN` only from the environment (and `.env`), never from `nogat.toml`; `config show` reports `present`/`missing` without the value, and a token key in the file is reported as ignored (`config_file.ignored`). | A token in the settings file. |

Document `imgw-config/1`: `config_file`, `keys` (value, `source` `default`/`env`/`dotenv`/`file`, `name`), `credentials`, `store` (root, source, size without double-counting hard links). The store root without `IMGW_STORE_ROOT` is `null` until the write-path task introduces `<data_dir>/imgw`. | A REST route/MCP tool with the server configuration. |

The user has one place for settings shared with the other Nogat tools and one command that shows where each value comes from. The write-path task changes `IMGW_STORE_ROOT` to `IMGW_ROOT`, sets the default root `<data_dir>/imgw` (and reports it in `config show`), and must treat `api_keys.json` in that directory as a file outside the store layout.

## ADR-006: Message catalog and English machine output

**Date:** 2026-10-24  
**Status:** Accepted  
**Standard:** Nogat 1.0, AGI-9.1, AGI-9.2, AGI-6.4, DEV-2.1, DEV-2.3, ECO-042; ADR-004 D2–D3 (the limits it recorded)  

### Context and options

AGI-9.2 makes every machine output English (`--json`, the error line of the CLI, MCP results,
REST without `Accept-Language`, OpenAPI, `AGENTS.md`, `llms.txt`) and leaves Polish to the
human-readable output on request; DEV-2.3 keeps user-facing text in translation resources, not
inline. ADR-004 translated only the catalog texts (`help_en`, `description_en`, `title_en`) and
left the `detail` of every error, the text of every notice and the progress lines Polish, so an
agent got Polish by default. Options: (a) gettext with `.po` files; (b) `locales/pl.toml` keyed by
the English sentence; (c) Python catalogs keyed by English IDs with both texts side by side; (d)
English literals at the raise sites and a Polish dictionary keyed by the sentence.

### Decisions D1–D7

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Catalog.** The package `imgwtools.messages`; one module per area (`messages/<area>.py`) with `MESSAGES: dict[str, Text]`; `Text(en, pl)` (English first); the key is `<area>.<name>` in snake_case; placeholders are `str.format` fields with plain names (a brace in the text is `{{`). ### Consequences

An agent reads the same English text whatever the user's setting, and a Polish user keeps Polish human output. Each area moves in its own commit (exceptions, notices, CLI, REST, MCP, guide), so the defaults of an interface flip together with the texts it shows. A new text costs two strings in a catalog and one `message("<key>", name=value)` call; the guard test fails on a missing translation, a wrong placeholder, an unused entry and a stray Polish literal. ## ADR-007: Data output: plain mode, the store and the default root

**Date:** 2026-10-24  
**Status:** Accepted (the author approved the Nogat convention on 2026-10-24; this ADR applies it to IMGWTools); the project parts of D2 and D8 superseded by ADR-008 (2026-10-31)  
**Standard:** Nogat 1.0, DEV-19.1 to DEV-19.20, DEV-18.2, AGI-3.4, AGI-5.8, ERR-1, ECO-051; changes D3 and Q3 of ADR-001  

### Context and options

IMGWTools wrote data in three unrelated ways: the versioned store with a required `--root` (and `IMGW_STORE_ROOT` for the CLI), a plain archive download to `--output` (default `./data/downloaded`, `.part` files, no check of existing files) and exports to `--path`. A nested store was recognised by Kartograf's sidecars, not by a marker, and the store statuses said `created` where Kartograf says `new`. ECO-051 and DEV §19 give every tool with a store the same two modes. Options: (a) keep the three paths and add aliases; (b) one convention for every writing command, as DEV §19 says (chosen); (c) a shared store library (rejected in the Nogat plan: a dependency between projects). IMGWTools 3.0.0 is untagged, so the breaking changes land before its first release without migration.

### Consequences

An agent or a script writes without a flag (the default store), writes plain files with `-o`, and gets the same names, errors, plan and `files[]` as in Kartograf. A call that wrote to `./data/downloaded` now fails with a hint or writes to the store. The default root `<data_dir>/imgw` also holds the API keys of the server, which is why the marker, not emptiness, decides what a root is. The plain engine (`imgwtools.output`) is written once and shared by the three commands and the exports. Consumers that read `status == "created"`, `DownloadReport.output` or the exports' `path` (Retman, Archiwista, Hydrolog) change with the pin (PROGRESS).

### Open questions

- Whether `store sync` in plain mode should offer a freshness check against the server (HEAD) before it replaces a file; it replaces on `--force` only, as DEV-19.9 says.
- Whether `series build` of a plain-mode tree should exist (DEV-19.18 makes derived data from stored versions store-only).

### Errata

**2026-10-25 — D6 (what a reader needs of the marker).** D6 says the marker "keeps `created_by`"; it is a field the writer writes, not one a reader needs. DEV-19.12 asks of a marker at least `schema`, `tool`, `created_at` and `producer_version`, and `open_store` has always taken any marker whose `schema` is `imgw-store/1`, while `store_info`, `iter_store` and every reader behind `current_version` refused a marker without a `created_by` text (`invalid_marker`). A root the writer had opened and completed (`prepare_store` adds `tool`, `created_at` and `producer_version`, never `created_by`) therefore could not be read, which Archiwista found. The reader now needs only `schema`, as `open_store` does (one rule on both sides, held by a test over the markers each side takes or refuses); `created_by` stays in the marker `init_store` writes, the packaged `imgw-store/1` schema lists it as an optional field instead of a required one, and the marker never gains it afterwards. The message `reader.marker_has_no_valid_created` is removed. This only widens what a reader accepts, so the contract stays `imgw-store/1`.

**2026-10-25 — D9 (the typed sidecar).** D9 says the sidecar already has the DEV-19.16 core; the typed `Meta` that `read_meta`, `iter_store` and `current_version` return now exposes the two fields of it that the reader validated and dropped, `producer` and `producer_version` (a consumer that cannot read them states the package itself and loses the version of an older write). They are the sidecar's own values: a version written by an earlier release keeps its older number and the version of the reading package never stands in, and since `imgw-meta/1` requires both, a sidecar without one stays `invalid_meta` and is refused, not filled in. The contract test of the sidecar core compares them with the file for every kind of version of both providers. Both fields are optional in the dataclass (defaults `"imgwtools"` and `None`), so `imgw-meta/1` and the constructors of `Meta` are unchanged.

**2026-10-25 — Consequences (the requests of Archiwista, the incremental scan).** Archiwista asked for four additions to the read API, all inside `/1` (AGI-4.1) and none a change of the files: the marker that a reader needs only `schema` of (D6, above), a code beside each text of `StoreInfo.problems` (`problem_codes`; the vocabulary `missing_store`, `missing_marker`, `invalid_marker`, `unsupported_store` is the one `iter_store` already used and is not renamed), `Meta.producer` and `Meta.producer_version` (D9, above) and an `iter_store` that takes the versions a consumer already knows. The last is `iter_store(skip_versions=…)`, a mapping of the version directory (relative to the root, with `/`) to the names of its data files: the shape of `ScanScope.known_versions` of Archiwista and of `skip_versions` of Kartograf (AGI-1.2). Such a version comes back with `skipped=True` and no `meta`, without its directory being listed, its sidecar read or its file measured; a version never changes, which is why the caller can vouch for it. The scan still lists the slots, so a new version, a problem and a version that is gone show as in a full scan, and an observation is still checked against the content fields of the version it names (that sidecar is read on demand). Rejected: a "since" time, which says nothing of a removed, replaced or broken version; a plain collection of directories, which would list each of them to find the main file of an archive; an option of `store scan`, because a list of known versions does not belong in a query string or a command line, so the parameter exists in Python only.

**2026-10-25 — D4, D5, D6 (refusals of the output directory and of the root; Nogat decisions R1 and R2).** D5 says an `output_dir` that is, lies inside or would enter a store is `conflict`, and D5 as built listed every target of a refused directory in `details.paths`; D4 and D6 say the plan shows the refusal of the root and the run raises it, and as built only `nested_store` was a conflict action of the plan, `not_empty` was a `check_failed` action of `store init` or an error of the other plans, and `store sync` and `series build` refused such a root with `store_unavailable`. Two rules, the same in Kartograf and set in Nogat DEV-19.6, DEV-19.10, DEV-19.11 and DEV-19.20, replace them. **R1:** when the plain output directory itself is, or lies in, a store, the run refuses it before any request (`refuse_directory`, so also before the request that names the PMAXTP cell) with `details.paths` the output directory; the reason applies to every target. A store found only below the directory, in a subdirectory a particular target would enter, is reported for that target's path (`plan_plain`, `refuse`), and so is the file of an export (`output`: its directory is not what the caller named). The `--check` plan keeps one `conflict` action per target. **R2:** in `--check` a root that the run turns away with `conflict` (`nested_store`, `not_empty`) becomes ONE `conflict` action for the root (`path` the root, status `unverifiable`, the plan `ok`, exit 0, no request; `PlanAction.reason` gains `not_empty`), and every run refuses the same root before any request (`refuse_root`). What the run refuses with another code is raised by the plan: a layout without a marker is `store_unavailable` (`no_marker`), and an unreadable marker (invalid JSON, no `schema`) is `data_error` (`details.reason="invalid_marker"`), which the writer now says in the plan and the run; `datasets download --check` no longer turns either into a `check_failed` action. The reader keeps `invalid_marker` as the problem code of `StoreInfo` and `iter_store`, so the test that held reader and writer to the same markers compares the code of the refusal (`store_unavailable` for another schema, `data_error` for an unreadable marker).

**2026-10-31 — D2, D8 (superseded by ADR-008).** The project commands are removed (ADR-008), so D2's project task without a `root` and the `project *` commands of D8's store-only class are gone; the store-only class is `store init`, `store catalog`, `series build` and the options `plan` and `series` of `store sync`.

## ADR-008: Projects move to Archiwista

**Date:** 2026-10-31  
**Status:** Accepted (the author approved option B of the Nogat plan on 2026-10-31, recorded as ECO-054)  
**Plan:** Nogat [`docs/plans/2026-10-31-archiwista-projects.md`](https://github.com/Daldek/Nogat/blob/main/docs/plans/2026-10-31-archiwista-projects.md), step 3  
**Standard:** Nogat ECO-054, ECO-020, HUB-5.2; supersedes the project parts of ADR-001 (D1, Q1, Q2, the version policy), ADR-002 (D1, D4, D9, D10, D11, D14, the breaking changes), ADR-003 (D2, D14 and its erratum, D17, D18), ADR-004 D5 and ADR-007 (D2, D8)  

### Context and options

ADR-001 gave IMGWTools a project manifest of its own, `imgw-project.json` (`imgw-project/1`: tasks of a data command and their pins by `version` and `sha256`), with the module `imgwtools.project` (about 3,100 lines) and the `imgw project …` commands, and ADR-003 D14 added restoring ČHMÚ pins by canonical content. Kartograf keeps the same shape in `kartograf-project.json`, and Archiwista has projects of its own (discovery of both manifests, owner and sharing, own data and snapshots, project jobs). One notion lived in three tools: every new project feature crossed three repositories, and a version could be pinned only through a producer's task. Neither producer has released projects (IMGWTools' last tag is v2.1.1; 3.0.0 is untagged), so they can leave without a migration (ECO-020). Options of the Nogat plan: (A) keep the producers' manifests, let Archiwista show one project over them and ask each producer for a "pin what the store holds" operation; (B) projects only in Archiwista, the producers keep download, check and the store and gain one function that gives the command of a stored version (chosen); (C) a shared project library imported by every tool; (D) release with the producers' projects now and move them later.

(D) Release the projects now and move them later: the release would publish an interface only to break it in the next one. |
| D2 | **What stays.** The store, its layout and its read API (`store_info`, `iter_store`, `current_version`, `read_meta`, the `read_*` functions); the sidecar `imgw-meta/1` with `content_sha256` and `content_form`, `CONTENT_FORMS` and `imgwtools.store.content`; the observation register `imgw-observation/1`; `run_command`, `check_command` and the plan `imgw-plan/1`; the read-only `series select` (`select_series`, `SeriesSelection`); `imgwtools.testing`. The sidecar's content fields and the observations are store facts that Archiwista matches its pins on, so ADR-003 D17 and D18 stay valid for the store and only their project-pin parts are superseded. | Removing the canonical content with the projects: Archiwista could no longer tell a rewritten ČHMÚ file with the same content from a changed one. |
| D3 | **Archiwista owns projects.** A project is a directory with `archiwista-project.json` (`archiwista-project/1`), written only by Archiwista; a pin names the producer, the store-relative `version`, its `sha256` and its `content_sha256` when the sidecar has one. IMGWTools neither reads nor writes that file; Archiwista's project jobs call `check_command` and `run_command`. | A producer schema that Archiwista reads, as before. |
| D4 | **No migration (decision D4 of the Nogat plan).** Existing `imgw-project.json` manifests are neither converted nor read: projects were never released, and nothing in IMGWTools recognises the file any more. | A one-off import into `archiwista-project/1`. |

### Consequences

**Breaking** for every caller of a removed name (`docs/CHANGELOG.md`, `[Unreleased]`); no released interface breaks, because 3.0.0 is untagged. The catalog loses eight commands and nine example calls, and `AGENTS.md` and `llms.txt` are regenerated without the project commands and flow. A store written while projects existed stays valid and readable: the manifests lived outside the store and the store files do not change. A directory with an `imgw-project.json` is ordinary user data that IMGWTools leaves alone. Retman removes its `imgw_projects` module (Nogat plan step 4) and Archiwista moves its project jobs onto `archiwista-project/1` (step 5).

### command_for_version

**Decision (D5).** Archiwista pins versions itself and, to check a pin for updates or restore it, needs the command that would fetch the pinned version again (Nogat plan step 3, third point; Kartograf's counterpart is `command_for_file`, KB-6). `command_for_version(version, *, root=None) -> CommandCall` rebuilds it offline and read-only from the version's sidecar (`imgw-meta/1`) and the place of the version in the store layout. `version` is the version directory, its main file (`StoreEntry.version`), its sidecar, the PMAXTP `response.json` or a station file of a series version, relative to `root` (an absolute path must lie in it); `root` defaults to `store_root()` like the other read functions. Only the sidecar is read, so a version whose data file is gone still gives its command (a restore). The result is the call `parse_command` reads from the canonical line of `format_command`: options as texts, `root` the absolute store root (a store command always names its root, ADR-007 D2), `run` empty; `format_command`, `check_command` and `run_command` take it. It is a Python function only: no catalog command reads it, as no catalog command reads a version's sidecar for a consumer (`store info` describes the root, `store scan` lists versions).

| Family | Call | Rebuilt from |
|---|---|---|
| IMGW-PIB archive (`pl.imgw.*` series datasets) | `store sync --datasets <key> --years <year>` (`--months <month>` of a monthly file) | the server path of the slot, checked against `request` (`server_path`, `year`, `month`) |
| ČHMÚ archive (`cz.chmi.hydro_daily`, `cz.chmi.meteo_daily`) | `store sync --datasets <key> --stations <code>` (`--years <year>` of a station-year file) | the same, with `request.station_code` and `request.param` |
| station list (`pl.imgw.*_stations`, `cz.chmi.*_stations`) | `store catalog --provider <provider>` | the provider of the dataset; the catalog downloads its lists |
| station catalog (`pl.imgw.stations`, `cz.chmi.stations`) | `store catalog --provider <provider>` | the catalog directory; `request.user_locations` must be `null` |
| series version (or one of its station files) | `series build --dataset <key>` | the series slug, checked against `dataset` and `request.dataset` |
| PMAXTP cell | `pmaxtp sync --latitude --longitude --method --ind-x --ind-y` | the point of `request`, the method and cell of the layout |

The call is the narrowest that selects the version's file, and it is checked offline (`store sync`'s own selection must contain the file); it may cover files beside it that the same options select (the `H`, `Q` and `T` files of a half-year, every element of a ČHMÚ meteorological station), each a plan item of its own. **Refused, never guessed**, with `unsupported` (the Nogat registry code, added to `ERROR_CODES` with exit 15 and HTTP 422) and `details.reason="command_not_rebuildable"` (with `details.version` and `field` or `server_path`; the text names how to pin the version as local data instead): a catalog built with a user's coordinates file (the sidecar records its name, not its path), a sidecar without a field the call needs (`request.user_locations`, `request.latitude`, `request.longitude`), and an archive file `store sync` does not select (a file name this release does not download). A missing version or sidecar (an unfinished publication) is `not_found`; a sidecar that is invalid is `data_error` with `details.version`, one that contradicts the layout (`dataset`, `request.server_path`, `year`, `month`, `station_code`, `param`, the PMAXTP method or cell) also with `details.field`; a path that is no version (an observation, a slot directory, outside the root) is `validation_error` with `details.option="version"`. Rejected: a plan line (`imgw …`) instead of the call (a consumer would parse it back); the widest call of a dataset (it would download far more than the pin); guessing the coordinates file of a catalog from its name (any file of that name would do).

## ADR-009: The tool is called Obserwator

**Date:** 2026-11-03  
**Status:** Accepted (the author decided the full rename, code included, on 2026-11-03; recorded as Nogat ECO-057); supersedes the note of `docs/OBSERWATOR_SPEC.md` (owner decision of 2026-10-17) that left the rename to the major release after 3.0.0 (working version 4.0.0)  
**Plan:** Nogat [`docs/plans/2026-11-03-imgwtools-to-obserwator.md`](https://github.com/Daldek/Nogat/blob/main/docs/plans/2026-11-03-imgwtools-to-obserwator.md), step 2  
**Standard:** Nogat ECO-057, ECO-056, ECO-022, HUB-5.2, AGI-4.1, AGI-5.2, DEV-18.2, DEV-18.3, DEV-19  

### Context and options

The tool was named after IMGW-PIB, the institute whose public data it reads; since 3.0.0 it reads ČHMÚ as well, so the institute's name on the distribution, the command, the variables, the store and every document id mixes the tool with one of its data providers. `docs/OBSERWATOR_SPEC.md` planned the name Obserwator for the major release after 3.0.0 (working version 4.0.0), together with a provider layer and an English API. The only release, 2.1.1 on `main`, has no store, no `IMGW_ROOT` and none of the document ids, which exist only on `develop`, so the moment before the first release from `develop` is the cheapest one. Options: (a) rename only the product and keep `imgw` for the command, the package and the ids (two names for one tool, and the institute's name on every identifier); (b) rename everything in 3.0.0 without aliases (chosen); (c) rename in 4.0.0 as planned (every id released in 3.0.0 would then need a `/2` with a transition period under the IMGW-13 policy, and every consumer would migrate twice); (d) aliases or fallbacks for the old variables, marker and ids (a compatibility layer for formats no user has, ECO-056).

### Decisions D1–D4

| ID | Decision | Rejected |
|---|---|---|
| D1 | **The name map (ECO-057).** The product Obserwator; the distribution and the import package `obserwator` (`nogat-obserwator` at ADOPTION_PLAN 6.1, where a final `imgwtools` release points to it); the command `obserwator` (`obserwator mcp`, `obserwator server`; the REST paths `/api/v1` are unchanged); the MCP tools and `operationId`s `obserwator_<group>_<verb>` and `obserwator_system_<function>` (the longest, `obserwator_current_hydro_states`, has 31 characters) and the MCP server `obserwator`; the variables `OBSERWATOR_<KEY>` (a key naming an IMGW-PIB endpoint would keep the provider, `OBSERWATOR_IMGW_<KEY>`; no setting is one); `[obserwator]` of `nogat.toml`, `<data_dir>/obserwator` and `<cache_dir>/obserwator`; the document ids `obserwator-<kind>/1`; the marker `obserwator-store.json` with `"tool": "obserwator"` and the staging directory `.obserwator-incoming/`; the producer `obserwator` of sidecars and markers and the Parquet key `obserwator_schema`; the catalog extensions `x-obserwator*` and the export headers `X-Obserwator-Status`, `X-Obserwator-Notices`; the problem type `urn:obserwator:error:<code>`; `ObserwatorError` and its subclasses; every other identifier naming the tool (`ObserwatorGroup`, message keys, test names). The table of old and new names is the first entry of `docs/CHANGELOG.md` (`[Unreleased]`). | Keeping `imgw` for the command, the package or the ids. |

| D3 | **No alias and no migration (ECO-056).** An old variable and the section `[imgw]` are ignored; a store, sidecar, plan or envelope with an old id or the marker `imgw-store.json` is neither read nor converted, as only development builds wrote them. | Fallbacks for `IMGW_*`; a reader of `imgw-*/1`. |
| D4 | **Only the names change.** The rename changes no behaviour, layout, field or version number (3.0.0); the provider layer, the English API and the other proposals of `docs/OBSERWATOR_SPEC.md` stay proposals for a later release. | The rename together with the provider layer of the spec. |

## ADR-010: Result, error and catalog documents follow the Nogat standard 1.0

**Date:** 2026-11-04  
**Status:** Accepted (the author started the plan on 2026-11-04; release 3.0.0 blocker B6)  
**Plan:** Nogat [`docs/plans/2026-11-04-obserwator-agent-contracts.md`](https://github.com/Daldek/Nogat/blob/main/docs/plans/2026-11-04-obserwator-agent-contracts.md), decisions D1–D7  
**Standard:** Nogat AGI-2.4, AGI-3.2, AGI-3.3, AGI-3.4, AGI-4.1–4.4, AGI-5.6, AGI-6.3, AGI-6.5, ERR-3  

### Context and options

ADR-002 gave the CLI, REST, MCP and Python one catalog and one envelope, but in shapes of their own: the envelope had no `tool` or `version`; a list command returned `{items, total, limit, offset}` and paged by `offset`; notices carried `text` and a level `error`; the CLI and MCP error was `{code, detail, details}`; `command_schema` gave the JSON Schemas of the options; and the CLI always printed JSON. The Nogat standard 1.0 fixes the result (`result-1`), error (`error-1`) and catalog (`commands-1`) documents and a `--json` flag for every tool, and Kartograf and Hydrolog already follow it. Options: (a) translate at the consumers (every consumer keeps a mapping, and agents reading the guide meet another shape than in the other tools); (b) adopt the standard documents before the first release from `develop`, when no released interface breaks (chosen).

### Decisions D1–D7

| ID | Decision | Rejected |
|---|---|---|
| D1 | **Envelope.** `obserwator-result/1` gains `tool` (`"obserwator"`) and `version` (`__version__`); `items` stays absent until a batch command reports units. | A version only in the catalog. |
| D2 | **Paging.** A list command returns the page's items as `result` and the envelope's `page` `{total, next_cursor, truncated}`; `offset` becomes `cursor` in the CLI, REST and MCP: an opaque URL-safe base64 of the next index, a malformed one refused with `validation_error`. Every result document has its own `schema` `obserwator-<kind>/1`; notices are `{level, code, message}` with the levels `info` and `warning`. | Keeping `offset` beside `cursor`. |
| D3 | **Error document.** `obserwator-error/1` `{schema, code, title, message, hint?, details, exit_code, command?}` in English is the last stderr line of the CLI and the MCP error; `title` comes from the registry, `hint` from the message catalogue or the raise site (`ObserwatorError.hint`); REST keeps problem+json and adds `hint`. `message` is the former `detail`; the Python attribute keeps the name `detail`. | Renaming the attribute (every `except` block of the consumers changes for no reader's gain). |
| D4 | **Output for a person.** `--json` prints exactly the envelope; without it the CLI prints one generic summary (`cli/_render.py`) in the `--lang` language; the streams are unchanged. `--json` and `--lang` are run flags of `parse_command` and `format_command`, not catalog options, as in Kartograf. | A renderer per command; JSON by default. |
| D5 | **Catalog.** `command_schema` follows `commands-1`; the JSON Schemas of the options become internal (`_input_schemas`) and feed the MCP `inputSchema` and the OpenAPI bodies. `commands list` stays the summary `obserwator-command-list/1`: the full catalog in `commands-1` exceeds the 50 kB document limit, as in Kartograf and Hydrolog; the deviation from the wording of AGI-2.4 is raised in Nogat. | `commands list` as the full `commands-1` document. |
| D6 | **Copies of the standard.** `schemas/nogat/` holds Nogat's `result-1`, `error-1`, `commands-1` and the error registry (its README records the commit; refreshed from `std-1.0` at the tag); contract tests validate every document of the four interfaces against them. | Fetching the schemas from Nogat in the tests (network in the gate). |
| D7 | **Records.** This ADR and a Breaking entry with migration lines in `docs/CHANGELOG.md`. | — |

### Consequences

**Breaking** for every reader of the envelope, the error, the catalog and the CLI stdout (`docs/CHANGELOG.md`, `[Unreleased]`, with the migration lines); no released interface breaks, because 2.1.1 has none of them and 3.0.0 is untagged. `AGENTS.md` and `llms.txt` are regenerated and every call that reads output uses `--json`. The consumers follow in the order of the Nogat plan (HUB-5.2) through the pin set `candidate-1`: Retman and Archiwista read `page`, `cursor`, the notice and error `message` and call the CLI with `--json`; Hydraulik and Hydrograf use only `fetch_pmaxtp`.
